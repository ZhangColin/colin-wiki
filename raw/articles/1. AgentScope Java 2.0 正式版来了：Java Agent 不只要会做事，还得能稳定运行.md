![[Image 39.png|AgentScope Java 2.0 正式版来了：Java Agent 不只要会做事，还得能稳定运行]]

在2026 年 7 月 10 日上午 11 点 10 分左右，AgentScope Java 在 GitHub 发布了 `v2.0.0` 。

2.0 这条版本线此前公开的是 `RC1` 到 `RC5` ，这次 tag message 写的是：

text

2.0 first GA release

也就是说，AgentScope Java 2.0 终于从候选版本走到了第一个 GA 正式版。根 POM 里的版本已经切到 `2.0.0` ，Java 基线是 17，官方 Quickstart 推荐 Maven 3.9+。

`io.agentscope:agentscope-harness:2.0.0` 已经可以从 Maven Central 下载。

有个小坑要注意：当前 tag 的根 README 里还有一段 `1.0.12` 的旧依赖示例。现在上手应以 v2 文档和根 POM 为准，不要照抄那段旧版本号。

这个时间点挺巧。

刚把 Spring AI 的模型接入、Tool Calling、RAG、MCP 跑顺，又开始接触 Embabel 的 Goal、Action 和 GOAP。现在 AgentScope Java 2.0 正式发布，很容易冒出一个问题：

text

Java Agent 已经有 Spring AI 和 Embabel，

为什么还要再看 AgentScope？

因为它们盯着的不是同一层问题。

## 一、Agent 跑起来以后，麻烦才刚开始

用 Java 调一次模型不难。

给模型挂几个工具，让它查资料、读文件、调用接口，也已经有成熟的实现方式。

真正做一个能持续工作的 Agent，工程问题会很快冒出来：

text

一次任务跑十几轮，状态怎么保存？

进程重启以后，能不能接着上次继续？

模型准备执行危险命令，谁来拦？

工具调用到哪一步，前端怎么实时展示？

上下文越来越长，什么时候压缩？

本地文件、Docker 和云沙箱，怎么切换执行环境？

日志、权限、限流和追踪，应该插在哪一层？

这些问题不属于某一次 Prompt，也不只是 Tool Calling 的问题。

它们更接近 Agent 的运行时工程：一个 Agent 怎么保持状态，怎么安全使用工具，怎么接受人工干预，怎么在长任务里继续工作。

AgentScope Java 2.0 的主线就在这里。

## 二、2.0 和 1.0 相比

AgentScope Java 1.0 并不简陋。

官方发布说明里，1.0 已经有多模型接入、 `ReActAgent` 、注解式工具、MCP、多模态、RAG、长期记忆、多 Agent Pipeline、流式输出和 Hook。

2.0 不是从零补齐这些能力，主要改了四件事：

- `ReActAgent` 改成无会话状态的执行核心，不再绑定某个“当前会话”。同一个实例可以服务多个会话； `HarnessAgent` 负责工作区、状态恢复、上下文压缩、沙箱、Skills 和 Plan Mode。
- `Memory` 、 `SessionManager` 、 `StatePersistence` 等状态接口，收敛为 `AgentState` 和 `AgentStateStore` 。
- 流式输出统一到类型化的 `streamEvents()` ，Hook 逐步迁移到五个阶段的 Middleware。
- 新增 `PermissionEngine` 、 `ModelRegistry` 、模型重试和备用模型切换。

这也不是只改 Maven 版本：旧 Pipeline 和 `PlanNotebook` 已被替换，旧 RAG、长期记忆接口进入弃用或重写阶段。2.0 的重点，是重新整理 Agent 的状态、事件、权限和运行环境。

## 三、Spring AI、Embabel、AgentScope Java 各管什么

把三个框架放在一起看，会更容易理解。

| 框架 | 更关注的问题 | 代表性抽象 |
| --- | --- | --- |
| Spring AI | 怎么把模型和 AI 能力接进 Spring 应用 | `ChatClient` 、Model、Tool Calling、Advisor、VectorStore、MCP |
| Embabel | 怎么围绕目标组织动作，并根据状态规划任务路径 | Agent、Action、Goal、Condition、Domain Model、GOAP |
| AgentScope Java 2.0 | Agent 执行过程中，怎么管理循环、状态、权限、事件和运行环境 | `ReActAgent` 、 `HarnessAgent` 、 `AgentStateStore` 、Workspace、Permission、Middleware |

Spring AI 更贴近应用集成。

比如一个制度问答服务，需要通过 OpenAI-compatible 接口接 DeepSeek、查 PgVector、调用内部制度工具，再把结果流式返回给前端。Spring AI 在这类场景里很顺手，因为它和 Spring Boot、配置体系、可观测性以及现有业务代码接得很自然。

Embabel 再往上一层。

它更关心任务如何建模：目标是什么，哪些 Action 可以执行，执行前需要什么条件，执行后会产生什么领域对象，规划器怎么找到一条能达成目标的路径。

AgentScope Java 2.0 走的是另一条线。

它并不要求所有任务都先建成 GOAP 规划问题，而是先把 Agent 的推理与行动循环跑稳，再补上长期任务需要的工作区、状态恢复、权限审批、事件流、沙箱和扩展机制。

所以，选型不必先争谁取代谁。

这里的分层只是用来理解关注点，不代表三者官方承诺可以直接组合。多数项目先选一个主框架就够了；确实需要跨框架时，还要验证依赖、模型适配和运行时边界，免得框架比业务还重。

关键不是哪个框架“更高级”，而是当前最难解决的问题落在哪一层。

## 四、先看懂 ReActAgent 和 HarnessAgent

AgentScope Java 2.0 里最重要的两个入口是 `ReActAgent` 和 `HarnessAgent` 。

### ReActAgent：先把推理和行动循环跑起来

`ReActAgent` 是核心执行引擎。

它把模型、工具、权限、人机确认、上下文、状态、中间件和事件系统组织在同一个循环里。

一次典型执行大致是这样：

text

收到用户任务

↓

模型判断下一步

↓

直接回答，或者请求调用工具

↓

权限系统检查工具调用

↓

执行工具并把结果放回上下文

↓

模型继续判断

↓

生成最终结果，或者进入下一轮

它解决的是 Agent 最核心的运行问题：模型如何在回答和行动之间来回切换，直到本轮任务结束。

这不等于任务一定能长期运行。

一次调用结束后，状态放哪里；同一用户的下一次请求怎么恢复；工具要在本机、容器还是云沙箱里执行；上下文过长怎么办，这些还需要更多工程能力。

### HarnessAgent：给执行循环装上长期运行需要的设施

`HarnessAgent` 是对 `ReActAgent` 的一层封装。

它没有重新发明一套推理循环，而是在原有循环的关键位置接入：

text

Workspace

会话状态持久化

长期记忆

上下文压缩

大工具结果卸载

子 Agent

沙箱

Skills

Plan Mode

Channel 路由

官方 Quickstart 也把 `agentscope-harness` 作为推荐上手依赖。

如果只是想研究最小 ReAct 循环，直接使用 `agentscope-core` 里的 `ReActAgent` 就够了。

如果目标是做一个能跨多轮、跨进程继续推进任务的 Agent， `HarnessAgent` 更接近实际入口。

它有点像给发动机装上油箱、仪表盘、刹车和底盘。发动机决定车怎么动，其他部分决定它能不能在真实道路上稳定地跑。

## 五、2.0 真正值得看的，不只是多了几个 API

AgentScope Java 2.0 的变化不少，但有几项特别能说明它的方向。

### 1\. 事件流不只返回文本

普通流式接口常见的做法，是不断返回文本片段。

但 Agent 的执行过程不只有文本。它还可能包含：

text

模型开始调用

文本增量

工具调用开始

工具执行结果

等待用户确认

外部执行返回

Agent 最终结果

`streamEvents()` 返回的是类型化 `AgentEvent` 流。

前端不必从一段混合文本里猜“这是不是工具调用”，可以根据事件类型分别展示模型输出、工具执行状态和审批请求。

这对 Web Agent 很重要。用户看到的不再是一个一直转圈的页面，而是任务执行到哪一步、在等什么、为什么停下来。

### 2\. 工具调用有明确的权限边界

模型请求调用工具，不代表工具应该立刻执行。

AgentScope 的 Permission System 会在工具执行前做判断。一次调用最终有三种处理方式：

text

ALLOW：允许执行

DENY：拒绝执行

ASK：先让用户确认

自定义工具检查还可以返回 `PASSTHROUGH` ，把判断交回权限引擎，再按规则和运行模式处理。

例如，读取普通项目文件可以直接放行；删除文件、执行高风险命令或者访问生产资源，可以拒绝或进入人工确认。

权限不是 Prompt 里的一句“请谨慎操作”。

它进入了工具执行链路。即使模型坚持要调某个工具，应用侧仍然可以根据规则和真实入参拦住这次调用。

### 3\. 状态不再绑死在 Agent 实例上

`ReActAgent` 把每次调用需要的可变状态放进 `AgentState` 。配置 `AgentStateStore` 后，框架会在调用前后自动加载和保存状态，并按 `(userId, sessionId)` 寻址。

这意味着同一个 Agent 实例可以服务多个用户和会话，每次调用根据 `RuntimeContext` 找到自己的状态。相同 `(userId, sessionId)` 的请求会串行执行，不同 session 可以并行。

裸 `ReActAgent` 不配置 `AgentStateStore` 时，不会把状态持久化到外部存储。 `HarnessAgent` 默认使用本地 `JsonFileAgentStateStore` ；多副本部署时，可以替换成 Redis、MySQL 等实现。

这比“给每个用户 new 一个 Agent，然后放进 Map”更接近服务端应用的管理方式。

不过要注意，能接 Redis 不代表应用自动具备了生产级可靠性。会话隔离、过期策略、幂等、并发控制和数据合规，仍然要由项目自己设计。

### 4\. Workspace 把任务逻辑和执行地点分开

有些 Agent 只查数据库、调 HTTP 接口，不需要独立执行环境。

但研发 Agent、数据分析 Agent、自动化运维 Agent 经常要读写文件、执行命令、安装依赖，甚至运行模型生成的代码。

这些动作直接跑在应用宿主机上，风险很高。

Workspace 和 Filesystem 抽象让同一套 Agent 逻辑可以接本地文件系统、共享存储或沙箱环境。任务逻辑关心“要读取哪个文件、执行什么动作”，执行环境负责“这些操作在哪里发生、如何隔离、怎么恢复”。

这层拆分为本地开发、容器执行和云沙箱之间的切换留出了空间。

### 5\. Middleware 给运行过程留了扩展点

日志、鉴权、租户上下文、限流、模型降级和链路追踪，不适合散落在每个 Tool 和 Agent 里。

AgentScope Java 2.0 的 `MiddlewareBase` 提供了几个关键切入点：

text

onAgent

onReasoning

onActing

onModelCall

onSystemPrompt

开发者可以只实现需要的 hook。

比如在模型调用前记录 token 预算，在工具执行前检查业务权限，在 system prompt 构造时注入租户信息，或者用 OpenTelemetry 记录一次 Agent 执行经过了哪些步骤。

这和 Spring 开发里熟悉的拦截器、过滤器思路很接近：横切能力集中处理，业务动作保持干净。

## 六、它和 Embabel 最容易混在哪

Embabel 和 AgentScope Java 都在做 Java Agent，也都不满足于“调一次模型”。

两者最容易被混在一起的地方，是都提到了任务推进。

但它们的切入点不同。

Embabel 更强调目标、动作、条件和规划。开发者先描述有哪些 Action、目标是什么、领域对象如何变化，再让规划器根据当前状态寻找路径。

AgentScope Java 的 `ReActAgent` 更强调运行中的推理与行动循环。模型根据上下文选择工具，工具结果回到上下文，模型继续判断。 `HarnessAgent` 再为这条循环补上工作区、记忆、状态、权限、沙箱和子 Agent 等设施。

拿“研发执行 Agent”举例：

text

用户：检查这个项目为什么启动失败，并给出修复建议。

用 Embabel 建模，可以把它拆成：

text

Goal：得到可验证的启动失败结论

Action：读取构建配置

Action：检查 JDK 和依赖

Action：运行构建命令

Action：分析错误

Action：生成修复方案

框架根据条件和中间结果规划执行路径。

用 AgentScope Java，更自然的关注点可能是：

text

Agent 在哪个 Workspace 里读项目？

运行构建命令前要不要审批？

命令执行过程怎么流式返回？

工具结果太长怎么卸载？

任务中断后怎么恢复？

下一轮还能不能接着同一个 session 继续？

一个偏任务模型，一个偏执行运行时。

真实项目里，两类问题往往同时存在。选型时没必要先站队，先看自己现在是在为“路径怎么规划”发愁，还是在为“Agent 怎么长期、安全地跑”发愁。

## 写在最后

Spring AI 解决的是 AI 能力怎么进入 Spring 应用。

Embabel 让目标、动作、条件和领域对象有了更清楚的组织方式。

AgentScope Java 2.0 更关心 Agent 开始行动以后，状态怎么留、权限怎么管、过程怎么看、环境怎么隔离，以及任务中断后能不能继续。

它们之间有重叠，但关注点不同。

AgentScope Java 2.0 最值得看的地方，不是又多了 `ReActAgent.builder()` 和 `HarnessAgent.builder()` 两个入口，而是它把 Agent 当成一个需要长期运行和接受治理的软件系统来设计。

接下来我也会从 `HarnessAgent` 开始，先用一个 Web 接口把第一个 Agent 跑起来，后续再逐步加入工具、权限确认、SSE事件流、Workspace、状态恢复和Docker沙箱。
