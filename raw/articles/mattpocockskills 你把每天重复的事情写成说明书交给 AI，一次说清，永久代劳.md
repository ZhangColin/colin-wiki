## 前言

故事是这样的。

你每天重复做很多事。早上打开邮箱，清掉昨晚堆下的通知。上班先看一眼 GitHub，处理新 issue、回 PR 评论。每周五做一次依赖升级。每个月整理一次发票。

这些事有个共同点：它们不是一次性任务，而是定期回来找你的循环。每一次做，你都要重新打开页面、重新读一遍上下文、重新判断一遍，然后重复上一次的操作。

问题来了：你明明有 AI，为什么这些事还是自己在做？

你可能会说，AI 帮不上忙，它不知道我每天要看哪些东西、怎么分类、怎么处理。

对，问题就出在这。AI 不知道你的循环长什么样，所以帮不上忙。而你自己，可能也没仔细想过这些循环长什么样。

`/loop-me` 干的事，就是陪你把这些循环一个一个说清楚，写成一份份「工作流说明书」。说清楚之后，委托就是顺理成章的事。

它不是写代码的技能，也不是分析大工程的技能。它做的事很朴素：帮你发现生活里那些值得委托的循环，再用追问的方式，把每个循环的细节逼到台面上，写成一份 AI 能直接照做的说明书。

写这篇专题之前，先把话说在前面。loop-me 目前还在 Matt 的仓库里挂着「in-progress」的牌子，属于还没毕业的草稿技能。它不在插件包里，也不在官方 README 的技能列表里，得自己从源码装。但这不妨碍它现在就能用，也不妨碍它值得学。草稿状态恰恰说明这是个新方向，Matt 自己还在打磨。

## 一、先戴上 loop 眼镜

loop-me 的说明书开头有一句话，我读了好几遍，越想越觉得有味道。

把生活想象成一圈圈的循环，你会发现它的活动到底有多可预测。可预测，才值得委托。

一个 loop 就是你生活中反复出现的模式。你的职业生涯是一个大循环，你的一周是一个中等循环，你的每个早晨是一个小循环，你每天重复的某个动作是一个更小的循环。大循环套小循环，小循环套更小的循环。

这个视角有什么用？用一句话说：可预测的事才值得委托，而大多数你以为「临时处理」的事，其实是可预测的。

举个最普通的例子。你每天早晨处理通知，看起来是随机的，来什么处理什么。但戴上 loop 眼镜再看：通知的类型就那几种（新 issue、PR 评论、@ 提醒），处理动作也就那几种（回复、分类、转交、忽略）。类型有限、动作有限，这就是一个可预测的循环。可预测，就可以被描述，就可以被委托。

loop-me 还有一层意思，比上面那句更妙：它不仅要帮你把你已经意识到的 loop 说清楚，还会主动提议你没注意到的 loop。你可能根本没想过「每月给客户开发票」是个可以委托的循环，直到它被指出来。

## 二、什么时候用 loop-me

loop-me 是 grill 家族的新成员。先回顾一下第四课讲的 grill 三兄弟。

grilling 是内核循环，模型自动调用。

grill-me 是轻量壳，你手动输入，问完就走，针对单个计划或设计做无休止追问。

grill-with-docs 是重量壳，问完还写文档，边访谈边建模，产出 CONTEXT.md 和 ADR。

loop-me 是第四个成员，它问完之后产出的东西专门且唯一，就是 workflow spec。它是 grill 家族里唯一一个把「访谈」和「委托」直接连起来的成员。

```
grilling（内核循环）
├── grill-me（问完就走，不留产物）
├── grill-with-docs（问完写 CONTEXT.md / ADR）
└── loop-me（问完写 workflow spec，工作流说明书）
```

什么时候该用 loop-me？判断标准很简单：这个事是不是会反复发生？

反复发生的，才值得写成说明书。一次性的事，直接 grill 完就干，别写 spec。你每天处理的 GitHub 通知值得写，你下周要做的那个新功能不值得写，那是一次性工程，走 to-spec / to-tickets。

那跟 wayfinder 的边界呢？wayfinder 管「一次会话装不下的大工程」，产出的是决策不是可交付物，探完路就交给 to-spec。loop-me 管「反复发生的循环」，产出的是工作流说明书，写完就能交给执行者跑。一个管一次性的大，一个管反复性的小，不冲突。

顺带说一句，loop-me 跟「让 AI 写代码」也不冲突。loop 里如果需要写代码，说明书里写清楚就行，执行时该走 tdd 走 tdd，该走 code-review 走 code-review。loop-me 只负责把循环描述清楚，不负责代替其他技能干活。

## 三、四个词，把循环说清楚

loop-me 给了一套词汇，专门用来描述循环。四个词，我一个个拆。注意，这套词汇不是 checklist，不是说每个 workflow 都必须凑齐这四个词。它是用来在你需要描述某个循环时，让描述更准确的语言。loop-me 原话是：不强制任何结构，一个 workflow 可以没有 AI，可以没有检查点，可以没有计划，除非追问证明它需要。

### Trigger，触发器

一个 loop 每次是怎么被点燃的？两种：事件或者计划。

事件触发，来了一个事件就跑一次，比如来了一封新邮件、来了一个新 issue。计划触发，到点就跑一次，比如每天早上九点。

loop-me 的立场很明确：事件触发通常更高效。为什么？因为它只在有事要处理时才运行，不会空转。一个「每天早晨检查收件箱」的计划触发，一天里大部分时候收件箱是空的，白白浪费一次运行。而「来新邮件才处理」的事件触发，邮件一到就处理，不来就安静待着。

写 spec 时，Trigger 是第一行要写清楚的：什么事件，或者什么计划，会启动这个循环。

### Checkpoint，检查点

一个 loop 里，总有一些地方需要真人看一眼、拍个板。这个「人在回路」的位置，就是检查点。

有的 workflow 一个检查点都没有，全自动跑完。有的 workflow 干脆不用 AI，就是一段脚本加一个提醒。loop-me 明确说：不强制要有检查点，也不强制要用 AI。要不要检查点，取决于这个循环里有没有需要人判断的事。

### Push right，把检查点往右推

这是整个词汇表里我最喜欢的一个词。意思是：把检查点尽量往后推，推到实在推不动为止。

翻译成人话：在打扰人类之前，把能做的活全做完。让人类只被问一次，而且是在最后问，问的时候所有东西都已经准备好了。

为什么这很重要？因为每一次把人类拉进来，都是有成本的。你正在写代码，AI 跳出来问一句，你的心流断了。push right 的本质，是把人类被打断的次数压到最低，把每次打断的价值提到最高。

### Brief，简报

检查点出现的时候，给人类看什么？

答案是 brief，不是原始输出。一份好的 brief 是紧凑的、可以直接做决定的摘要：产出了什么、为什么、以及指向产出物本身的链接。人类读的是简报，不是草稿。

这个原则太重要了。你可以想象没有 brief 的世界：AI 把 20 封邮件原文加分类理由全部贴出来，你花十分钟读完，然后发现它把两封搞反了。有了 brief 的世界：AI 给你五句话，每封邮件一句话结论加一个链接，你三十秒扫完，说一句「第二封不对，重分」。

速度就是一切。审阅越快，你越愿意把更多循环交给 AI。审阅越慢，你越抗拒委托，循环就越留在自己手里。

## 四、一份 spec 长什么样

说了一堆概念，看实物。下面是一份完整的 workflow spec，场景是「处理 EShop 项目的 GitHub 通知」。这份 spec 是按 loop-me 的词汇写出来的，可以直接存成 `workflows/github-notifications.md` 当示范。

```
# GitHub 通知处理

## Trigger
事件：GitHub 上有新的通知（新 issue、PR 评论、@ 提醒）

## 执行步骤
1. 拉取所有未读通知
2. 过滤：机器人通知、自动关闭的依赖通知直接归档，不进入后续步骤
3. 分类：新 issue（bug / 需求 / 提问）、PR 评论、@ 提醒
4. 去重：搜索是否已有相同内容的 issue 或评论
5. 为每条保留的通知生成摘要

## Checkpoint
一个，在最后：把摘要交给人审

## Push right
第 1 到第 5 步全部由 AI 完成，人类只审最终摘要，不接触原始通知

## Brief 格式
- 每条通知一句话：类型、主题、建议动作
- 建议动作后附原始链接
- 若怀疑分类有误，标出待确认
```

这份 spec 有没有问题？有，而且我故意留了一个。它没有写「完成动作」：人审完之后，通知要怎么处置？归档、标记已读、转 issue？这个问题不解决，实现者就不知道最后一步该干什么，spec 就不算完成。

这正是下一节要讲的事。

## 五、手把手，grill 一场出来

loop-me 的会话不是直接写 spec，它是一场有状态的 grilling 访谈，一次一个问题，每个问题附一个推荐答案，问到你把所有分支都问透为止。

什么叫问透？loop-me 给的完成标准是这么写的：一份 workflow spec 算完成，当实现它的 agent 能不问一个问题就把它建出来。grill 到那时候为止，只要还有一个问题悬着，就什么都不算完成。

这个标准非常狠。它不是「差不多清楚了」，而是「实现者不需要再问任何问题」。翻译过来：spec 里每一个可能让执行者卡住的细节，都必须在访谈里被问出来、写进去。

下面模拟一场真实的 loop-me 会话。场景：你受够了每天早上手动处理 GitHub 通知，想把它委托出去。AI 开始提问。

第一问，这个循环的触发是什么？

推荐答案：事件触发。有新的通知才处理，不要定时轮询。通知少的日子里，一个定时任务空跑一小时，纯浪费。

第二问，处理到什么程度算完成？

推荐答案：产出 brief，不直接改代码。分类、去重、摘要都由 AI 做，但是否回复、是否关闭 issue，这些动作留给人类决定。理由：这些动作影响项目状态，属于决策，不是机械劳动。

第三问，检查点放在哪？

推荐答案：放在最后，一个检查点。AI 把所有通知处理完，一次性交一份 brief。不要处理一封问一次，那样你会被烦死。

第四问，检查点呈现什么？

推荐答案：brief。每条通知一句话加建议动作加链接。不要贴原始内容，不要贴分类理由的完整推导。

第五问，人审完之后，通知怎么办？

推荐答案：归档并标记已读。确认要跟进的转成 issue 并标记。这一步写进 spec，作为完成动作。

六问下来，之前缺的「完成动作」补上了，spec 从「大概能用」变成「实现者可以直接照着建」。把第五问的答案补进上一节的 spec，最后一步变成：

```
6. 人审完 brief 后：确认跟进的转成 issue 并标记，其余归档并标记已读
```

补充说明一点，这场会话是我按 loop-me 的规则模拟的教学示例，不是真实录音。但规则是真实的：一次一个问题、每题附推荐答案、问到 spec 完成。

## 六、工作区：说明书存在哪

loop-me 把当前目录当成有状态的工作区，里面两样东西。

`workflows/*.md` ，每个 workflow 一个文件，是事实源。spec 的每一次修改都落在这里，它就是最终交付物。

`NOTES.md` ，关于你的世界的原始笔记：你用哪些工具、处理哪些渠道、你自己对这些东西的称呼。当 NOTES.md 是空的或者很薄的时候，loop-me 会先访谈你，把你的世界摸清楚，再开始指定 workflow。

这里有个很妙的机制：访谈过程中冒出来的模糊说法，会被收敛成规范术语，记录进 NOTES.md。比如你随口说「每天清一下收件箱」，访谈里澄清出「收件箱」指 Gmail 主收件箱，「清一下」指归档加回复紧急邮件，这些就变成 NOTES.md 里的规范术语。下次再提到「清收件箱」，大家都明白指的是什么。

这也解释了为什么 loop-me 是有状态的。它跨会话记住你的世界，这次访谈的产物（NOTES.md 里的术语）会成为下次访谈的基础。你用它的时间越长，它越懂你，后面指定新 workflow 的速度越快。

## 七、边界和误区

第一，不是所有事都值得委托。委托的前提是循环可预测、频率够高。一个月才发生一次、每次内容都完全不同的事，写 spec 的成本比自己做还高。loop-me 自己都强调：不强制结构，需要才写。

第二，workflow 不是越大越好。一个 workflow 一个循环，职责单一。把「处理通知」和「每周发布」塞进同一个 spec，两个循环的触发、检查点、brief 全不一样，写出来必然拧巴。拆开写。

第三，spec 写完了不等于事情做完了。spec 是给实现者看的说明书，实现、部署、持续运行是另一回事。loop-me 只管到「说明书可以交付」，后面该接什么接什么。

第四，别把它当检查清单。四个词是语言，不是模板。你的循环需要哪个词就描述哪个词，不需要的不硬凑。有的循环可能只有一个 Trigger 加一个 Brief，照样是完整的 spec。

## 八、为什么值得学

往回看这个系列，Matt 的整套技能其实在回答同一个问题：怎么让 AI 干活干得靠谱。前面几课答的是怎么让 AI 把活干好：问清楚需求、写好测试、审好代码。loop-me 答的是另一个方向的问题：怎么让 AI 替你干那些你根本没想过能交给它的活。

这个方向很容易被忽略。大部分人的注意力都在「怎么让 AI 写代码」上，很少有人停下来想「我生活里哪些事其实可以委托」。loop-me 的 loop 视角，就是帮你做这件事的。

它顺带教会你一件事，比 loop-me 本身更值钱：委托的前提是把事情说清楚，说清楚的前提是发现自己生活里的循环。这个能力，不依赖任何工具。

## 快速回顾

- loop 视角： 生活是循环中的循环，可预测的才值得委托

- 四个词： Trigger（事件触发通常更高效）、Checkpoint（人在回路）、Push right（检查点推到最晚，人类只被问一次）、Brief（读简报，不读草稿）

- 工作区： workflows/\*.md 是事实源，NOTES.md 记你的世界，模糊术语收敛成规范术语
- 不强制结构： workflow 可以没有 AI、没有检查点、没有计划
- 状态： in-progress 草稿技能，官方仓库 `skills/in-progress/loop-me` ，自己从源码装
