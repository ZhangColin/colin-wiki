## 前言

故事是这样的。

前六课，我们像拆零件一样，把每个技能单独拆开讲了一遍。开关（01）、地图（02）、词典（03）、访谈（04）、流水线（05）、反馈（06）。一个零件一个零件看过去，每一个你都觉得，嗯，懂了。

然后呢？

然后你打开一个真实项目，准备大干一场，突然发现，零件是零件，机器是机器。

单个零件谁都会看，怎么装到一起，才是真本事。

这一课，就是把前六课的零件，装成一台能跑的机器。我们用 EShop 的一个真实需求走一遍完整流程，优惠券叠加满减。这个需求挑得很刁钻，它同时考验共享语言（满减、物化级联）、访谈（叠加规则）、流水线（拆工单）、反馈（测试兜底），一个都跑不掉。

我们从拿到需求开始，到代码通过审查结束，一步步看每个技能在什么时候出场。

开始之前我想先说清一件事。说实话，写这一课我有点心虚，因为整套流程串起来看，你会发现它一点都不神秘，全是老东西。面试、写规格、拆任务、测试、调试、审查，这些都是我们干了三十年的活。区别只是执行者从人换成了 AI。

这个视角很重要，因为它决定你是把它当「工具」还是当「信仰」。当工具用，它帮你干活。当信仰用，它让你干活。

## 一、拿到需求，先别急着写

需求一句话，下单时，优惠券和满减可以叠加。

你当然可以直接跟 AI 说这句话。但六课下来你应该知道，这句话背后全是没说的决策。叠加顺序是什么？优惠券先减还是满减先减？超过实付金额怎么办？一张订单能用几张券？

每个问题都是一个 bug 的温床，先别急着写。

用 `ask-matt` 确认路由。

```
/ask-matt 下单优惠券叠加满减，该怎么走流程？
```

`ask-matt` 读你的描述，返回路线图，先用 grill 访谈，再走 to-spec 到 implement。它就是技能地图的导航员，你不记得用哪个技能时问它。

这个「导航员」角色，我挺喜欢的。技能多了，最大的成本是选择成本。我这个人有个毛病，工具越攒越多，真到用的时候反而选择困难。ask-matt 把这个选择交给 AI 自己，省的是你翻地图的时间。

## 二、访谈，让共享语言先省一半力气

打开 `grill-me` ，开始访谈。因为 EShop 有 CONTEXT.md（03 课建的），这次访谈比 04 课顺得多。

```
AI：优惠券叠加满减，先算哪个？
    我们术语表里满减是 FullReduction，物化级联是 MaterializationCascade，
    你说的叠加是指同一订单行同时应用两者？

你：对。先满减后优惠券。

AI：优惠券类型有哪些？满减券、折扣券？
    超过实付金额时优惠券怎么处理？

你：满减券。超过部分不找零，最多减到 0。
```

注意两个细节。

第一，AI 已经在用你的词。「FullReduction」「MaterializationCascade」直接从 CONTEXT.md 来，没有绕圈解释。03 课的投入在这里回本了。

第二，问题一次只问一个维度，你不用在问题海里挣扎。

访谈结束，四个决策全部确认。

注意看这次的访谈和 04 课有什么不同，AI 没有问「什么是满减」，它直接用术语表里的词和你对话。这就是共享语言的复利效应。第一次建 CONTEXT.md 花半小时，之后每一次访谈都在省这半小时。

## 三、沉淀，对话变成规格

访谈结论还在对话里，用 `to-spec` 沉淀成文档。

```
[规格] 优惠券叠加满减
- 决策 1：叠加顺序，先满减后优惠券
- 决策 2：优惠券类型，仅满减券
- 决策 3：超过实付金额，最多减到 0，不找零
- 边界：单订单单券；叠加只作用于满减后的金额
```

这份规格发布到 issue tracker，可评审、可回看、可传下一个 AI。想改一条，改文档，不用重新聊。

这里我想强调一个常被忽略的好处，规格让「评审」这件事有了抓手。你跟 AI 聊出来的结论，没法让别人评审。写成规格，同事能看、能指出「叠加顺序是不是反了」。这是对话永远给不了的东西。

## 四、拆单，规格变成工单

`to-tickets` 把规格拆成带依赖的工单。

```
[工单 1] 定义优惠券实体与满减券类型（Coupon / CouponType）
  阻塞：无
[工单 2] 下单金额计算加入优惠券抵扣（叠加于满减之后）
  阻塞：工单 1
[工单 3] 处理超过实付金额的兜底（最多减到 0）
  阻塞：工单 2
[工单 4] 单订单单券约束校验
  阻塞：工单 1
```

每个工单独立可验证，依赖关系保证执行顺序。我们从工单 1 开始。

拆工单最容易被低估的价值，是它逼你把功能拆成「能独立验证的块」。这在演化式设计里叫小步走，每一步都能跑、能测、能回退。AI 编码尤其需要这个，因为 AI 一次做完大功能，错了很难定位错在哪一步。工单就是给 AI 装上了「分步执行」的骨架。

## 五、写码，implement + tdd 双剑合璧

`implement` 开始执行工单。工单 1 先定义优惠券实体，然后到关键的工单 2， `implement` 在边界处驱动 `tdd` 。

先写会失败的测试（红）。

```
@Test
void createOrderWithCouponStacking() {
    // 原价 1200，满 1000 减 50（满减），再用满减券减 100
    OrderVO result = orderService.createOrder(
        buildRequest(1200, coupon(100, CouponType.FULL_REDUCTION))
    );

    assertEquals(BigDecimal.valueOf(1050), result.getTotalPrice());
}
```

再写最小实现（绿）。

```
// 先满减，后优惠券
BigDecimal afterFullReduction = applyFullReduction(total);
BigDecimal finalPrice = afterFullReduction.subtract(coupon.getAmount());
if (finalPrice.compareTo(BigDecimal.ZERO) < 0) {
    finalPrice = BigDecimal.ZERO;  // 最多减到 0
}
```

跑测试，绿色。工单 2 完成，进入工单 3 的兜底测试、工单 4 的单券校验，一个接一个，红变绿再下一个。

这个「一个工单一个测试」的节奏，就是演化式设计最舒服的样子，每一步都有验证，每一步都能回退，出问题了精确到工单。AI 把它执行得又快又稳，这正是纪律的价值，让快的工具按稳的节奏走。

## 六、抓错，diagnosing-bugs 处理漏网之鱼

测试全绿，你以为结束了。

然后集成环境报了一个 bug，两张优惠券同时提交时，系统竟然都抵扣了？？？单订单单券的校验漏了。

`diagnosing-bugs` 开始排错。

```
复现：构造两张满减券的下单请求，复现双抵扣
最小化：定位到校验逻辑（工单 4 的约束）没有拦截第二张券
假设：校验只查了「请求里有没有券」，没查「订单上已有几张券」
插桩：打印校验入参，确认第二张券进入了抵扣
修复：校验改为「订单已应用券数 + 本次提交数 ≤ 1」
回归：跑全量测试 + 双券用例，全绿
```

六步走完，证据链完整，不是碰运气修好。

这个 bug 很有代表性，单元测试全绿，但集成环境出了问题。这正好印证了 06 课那句话，测试不是银弹，兜不住跨模块的交互。diagnosing-bugs 的价值，就是在测试兜不住的地方，用「先复现、后假设、再验证」的科学流程补上。

## 七、审查，code-review 把关

代码写完了， `implement` 的最后一个纪律是提交前走 `code-review` 。它分两条轴并行审查。

- 标准轴，代码符合 EShop 的编码约定吗？（@RestController、Result 包装、SLF4J 日志）
- 规格轴，代码忠实实现了规格吗？（先满减后券、最多减到 0、单订单单券）

两轴都过，才能提交。这条防线在 AI 时代尤其重要，AI 生成代码又快又自信，但只有人 + 审查流程能让它「可信」。

双轴审查是个很聪明的设计。单轴审查（只看标准或只看规格）很容易漏一半，代码很规范但做错了需求，或者需求做对了但风格一团糟。双轴逼 AI 两件事都检查一遍，这比只检查一样强得多。

## 八、回看，一次开发用到的全部技能

走完一次完整流程，把用到的技能列出来，你会发现前六课一个都没浪费。

| 阶段 | 技能 | 课 |
| --- | --- | --- |
| 路由 | ask-matt | 02 |
| 访谈 | grill-me | 04 |
| 沉淀 | to-spec | 05 |
| 拆单 | to-tickets | 05 |
| 写码 | implement + tdd | 05 / 06 |
| 抓错 | diagnosing-bugs | 06 |
| 审查 | code-review | 05 |

加上全程支撑的共享语言 CONTEXT.md（03 课），这八个环节构成了一个完整的 AI 编码工作流。

而这一切的起点，是 02 课那张「四坑 → 解药」地图，每个技能都对着一个坑，一个坑一个坑填完，流水线就自然形成了。

看到没，零件还是那些零件。但装在一起，它是一台能跑的机器了。

## 九、别一次全上，渐进引入

最后，也是最实用的一条建议。

整套流水线很完整，但完整不等于你第一天就要全部用上。你可能想，流程这么完整，干脆一步到位全上。我强烈建议你别。这不是为了省事，是为了让你和团队能分辨「哪个环节真的有用」。

我推荐的引入顺序。

```
第 1 周：只上 tdd。让 AI 写代码前先写测试，看测试兜住了什么。
第 2 周：加 CONTEXT.md。把术语统一，看 AI 是不是变聪明了。
第 3 周：加 grill-me。需求访谈，看是不是少跑偏了。
第 4 周：加 to-spec 到 implement。完整流水线。
```

每一步你都应该能回答一个问题，多上的这个环节，帮我解决了什么？如果答不上来，说明它不是你需要的那块。

这个「渐进替换」的思路，我用了大半辈子。我从 2004 年开始叫它 Strangler Fig，不推翻旧系统重建，而是一小块一小块地替换，直到旧的被慢慢绞杀。引入一套开发流程同理，不推翻你现有的方式，而是把 AI 编码里最有价值的那块先换上，让结果说话。结果说服人，比道理说服人快得多。

## 十、何时不要用

照例收尾。

这套流程是为「会持续演化的功能」准备的。一次性交付、不会改的功能，不值得养全套流程。

团队人数很少、项目很小，别照单全收。两三个人做个小项目，上全套流程是自缚手脚。挑 tdd 和 CONTEXT.md 两个就够。

当流程开始要求「按流程走而不是把事情做好」时，停下来。任何流程，包括这套，都会随着时间变成仪式。当团队开始「因为流程要求所以这么做」而不是「这么做有好处」，就该瘦身了。

用一句话总结这一课，整套技能的价值，不在流程本身，在它逼你做的那些事，先问清、先测好、先审完。流程可以裁剪，那些事不能丢。

回到开头。零件是零件，机器是机器。

前六课的零件，这一课装成了机器。机器跑起来了，下单、优惠券、满减、退款，一个功能一个功能地过，测试全绿，审查通过。

剩下的，就是你自己去装你的机器了。

装之前记住一句话，零件是用来装的，不是用来收藏的。

磨平一点信息差，哪怕只是你自己和昨天的自己之间，那一点。
