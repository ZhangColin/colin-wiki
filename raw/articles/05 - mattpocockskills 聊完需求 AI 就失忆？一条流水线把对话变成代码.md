#mattpocock #tdd #skills

## 前言

故事是这样的。

上一课，你让 AI 把 EShop 的下单需求访谈了一遍。四个问题，金额怎么算，库存怎么办，并发会不会重复，支付失败怎么回滚，你答得口干舌燥。结论清清楚楚，一条一条，躺在聊天记录里。

然后你关掉会话，下班回家。

第二天，你打开一个新会话，AI 眨巴着眼睛问你，上次说的那个下单需求，能再跟我说一遍吗？

你什么感觉？？？

我跟你讲，这种感觉我太熟了。访谈那半小时白聊了。那些结论像沙一样，攥在手里，风一吹，就散了。

你可能觉得，我记性好，明天还能想起来。别高估自己，也别高估 AI。你以为你记得的，和 AI 理解的，中间隔着十个脑补。

这一课，就是来解决这个的。

前四课我们解决了一个问题，怎么让 AI 听懂你要什么。grill 访谈加 CONTEXT.md 共享语言。但访谈只是第一步，访谈完的结论，还是「一段对话」，离代码还差得远。

这一课，我们把对话变成流水线。Matt 给这条流水线设计了三个环环相扣的技能。

```
grill 访谈结论
    ↓  to-spec：对话 → 规格文档
    ↓  to-tickets：规格 → 工单
    ↓  implement：工单 → 代码
可运行的 EShop 功能
```

每个环节各管一段，前一个的输出，是后一个的输入。我们跟着 EShop 的下单功能走一遍。

先说句实话。我第一次看到这套「对话 → 规格 → 工单 → 代码」的链条，本能地警惕。先写全规格，再拆工单，再实现，这听起来太像瀑布式开发了。我对瀑布式一向没有好感，在敏捷里摸爬滚打了这么多年，怎么绕回去了？但看完它是怎么工作的，我改变了一点看法。区别在细节里，我讲完你就明白。

## 一、to-spec，把对话变成规格文档

04 课访谈完，结论散在对话里。

```
金额：按订单总额算，满减配置在促销中心
库存：下单预占，不足拒绝
幂等：用户 ID + SKU + 时间窗口
回滚：支付失败释放库存
```

这些结论很清晰，但有个致命问题，它们只存在于你的聊天记录里。换一个会话，换一个 AI，这些结论就丢了，得重新访谈一遍。

这里我想起一句老话，口说无凭，立字为据。古人签契约，都知道要落笔成文。我们跟 AI 对齐需求，反而觉得聊过就算数了。聊天记录这个东西，是最不靠谱的存档，它没有结构，没法评审，换个工具连翻都翻不出来。

`to-spec` 解决的就是这个。把当前对话整理成一份规格文档，发布到你的 issue tracker。它不重新访谈，那是 grill 的事，它只做一件事，沉淀。

注意，是发布到 issue tracker，不是存进你的本地备忘录。为什么？因为 issue tracker 是 AI 和人都能读的地方，是你们的公共场地。你存进本地笔记，AI 看不到，等于没存。

在 EShop 里，跑 `/to-spec` 之后，你会得到一份类似这样的规格。

```
[规格] EShop 下单功能
- 决策 1：订单金额按订单总额计算满减（FullReduction）
- 决策 2：下单时预占库存，库存不足拒绝下单
- 决策 3：幂等键 = 用户 ID + SKU + 时间窗口
- 决策 4：支付失败释放预占库存
- 边界：并发下单不重复、满减规则来自促销中心
```

规格文档的好处，可回看，可评审，可传给下一个 AI。你想改其中一条，改文档，而不是重新聊一遍。

这里我要澄清一个关键点，这份规格，不是瀑布式那种开工前就写死全部细节的蓝图。它记录的是你已经访谈确认过的决策，不是预测未来会出现的需求。前者是记录，后者是猜测。这套流水线做的是前者，我支持。如果有人把它当成后者用，那是滥用，不是设计本意。

说到瀑布式，我又想起电力普及那会儿的事了。1880 年代，电力开始在美国普及，很多工厂主花大价钱买了发电机和电动机，装在自己的工厂里。但装完之后，很多人发现生产效率并没有提升。因为他们只是用电动机替代了蒸汽机，整个工厂的布局、流程、管理方式都没变。AI 时代最大的坑，也是这个，拿新工具走老流程。to-spec 不是让你把需求写死，是让你把已经想清楚的记下来，这两件事，差着十万八千里。

## 二、to-tickets，把规格拆成工单

规格文档是整个功能的「宪法」，但它太粗，AI 不能直接照着写代码。 `to-tickets` 把它拆成一批可以逐个执行的工单，每个工单声明自己的边界。

在 EShop 里， `/to-tickets` 会把上面的规格拆成这样。

```
[工单 1] 定义下单接口 DTO（CreateOrderRequest / OrderVO）
  阻塞：无
[工单 2] 实现订单金额计算（含满减 FullReduction）
  阻塞：工单 1
[工单 3] 实现库存预占与释放
  阻塞：工单 2
[工单 4] 实现幂等控制
  阻塞：工单 1
[工单 5] 支付失败回滚库存
  阻塞：工单 3
```

注意两个细节。

第一，每个工单都有明确的「阻塞」关系。工单 3 依赖工单 2，工单 5 依赖工单 3。这就是工单的依赖图，保证执行的顺序正确。implement 的时候，AI 会照着依赖图一个个来，工单 1 没做完，工单 2 不会开工。把「一次做一大坨」换成「一次做一小块，做完验证」，这就是拆工单的全部意义。

第二，每个工单是「探路」的。它不是最终实现，是帮 AI 走一步看一步的最小单元。写完一个，验证一个，再进下一个。

为什么拆？因为「实现下单功能」太大了。你让 AI 一次做完，它跑到一半就开始放飞自我，改到第五个文件的时候，已经忘了第一个文件里写了啥。拆成 5 个小工单，每个都能独立验证，跑偏了能及时拽回来。

拆工单这个动作，我其实是支持的，它跟我的演化式设计观不冲突。关键在于拆出来的每个工单是不是够小、能不能独立验证。能验证的工单，就是可执行的增量。不能验证的工单，只是听起来很细的计划。

## 三、implement，工单 → 代码

`implement` 是流水线的最后一环，按工单构建代码。它的三个关键纪律，前两个我们在系列里已经见过。

第一，在每个工单的边界处驱动 tdd，先写会失败的测试，再写实现。这个 06 课会细讲。

第二，提交前走 code-review，双轴审查，既看是否符合编码标准，也看是否忠实实现规格。

第三，严守工单边界。 `implement` 只做工单写的事，不顺手重构，不扩大范围。

在 EShop 里， `implement` 会从工单 1 开始，逐步推进到工单 5，每个工单都过一遍「测试 → 实现 → 审查」。5 个工单走完，下单功能完整落地。

「严守工单边界」这条纪律，我得单独夸一下。AI 编码最大的风险之一就是越界。做着工单 2，顺手改了工单 3 才该碰的代码，改出问题来，锅还扣不到任何工单头上。边界清晰，责任才清晰，验证才可能。

## 四、wayfinder，工作太大，先探路

`to-tickets` 适合「一个功能」的规模。但如果你的工作是「重建整个 EShop 的订单体系」，涉及几十个模块、几百个决策，工单拆完可能比代码还长。

这时候用 `wayfinder` 。它的思路，先不去想全部细节，把超大的工作画成一张调查工单地图，然后一张一张解决，直到通向目的地的路清晰了，再回到 `to-tickets` 拆具体的。

一句话区分。

```
功能级工作（一个下单）→ to-tickets 直接拆
项目级工作（整个订单体系）→ 先 wayfinder 探路，再 to-tickets
```

普通开发者 90% 的场景用不到 wayfinder，但知道它存在，遇到大项目时不慌。

wayfinder 的思路我熟。先别急着规划完整路径，先走一步看一步，每一步都只解决「下一个路口怎么走」。这跟 Strangler Fig 的想法同源，大改造不靠一次大爆炸，靠一块一块地替换。

## 五、为什么这么拆，三个原因

看到这你可能想说，这套流水线是不是有点绕。直接跟 AI 说「把下单功能做了」，不就行了？

我理解这种感觉。谁不想一句话搞定，对吧。但直接让 AI 做，你得到的是什么呢？一个黑盒。它怎么理解的需求，你不知道。它中间改了什么，你也不知道。出了问题，你只能从头到尾查一遍，等于把访谈、设计、实现重新做一遍。

你可能只是个普通开发者，就想让 AI 把手里的活快点干完，这套流水线看着像流程党的仪式感。我理解。但流程和仪式感的区别，就一条，每一步是不是能验证。能验证的，是流程。走完就忘的，是仪式。

三个原因，说明为什么拆。

第一，每步可审查。对话是流式的，没法回头审。规格文档可以逐条评审，改错一条影响最小。

第二，每步可复用。访谈结论沉淀进规格，规格沉淀进工单。下次 AI 掉线了、换人了，结论还在，不用从头聊。

第三，每步可验证。工单拆小了，每个都能独立测试、独立审查。跑偏在第一个工单就发现，而不是整个功能做完才发现全错了。

用我的话说，这不是绕路，是把不可控的大问题，切成五个可控的小问题。

但我得补一个提醒。这三个原因成立的前提，是这套流水线被当工具用，而不是当仪式用。如果它变成「每次改动都必须走全套流程」，那就是敏捷产业复合体的 AI 版，是我最反对的东西。流程服务于项目，不是项目服务于流程。

## 六、何时不要用

照例，再补一节边界。

改动极小时，别走全套。改一个字段名、修一个拼写错误，走「规格 → 工单 → 审查」纯属自虐。流水线是为「有规模的功能」准备的，不是为每一行改动准备的。

探索性工作，别走全套。你在验证「满减放数据库还是写死」这种技术可行性，预期代码用完就扔，不需要规格和工单。探索阶段就该快，快速试错才是目的。

团队只想快速试 AI 时，别上全套。如果你想先看 AI 到底能不能干活，让它直接写一版，比走完整流水线更能回答你的问题。先看能力，再上纪律。

一句话，流水线是用来管「确定要交付的功能」的，不是用来管「试试看的东西」的。

回到开头那个失忆的场景。

现在你知道怎么治了。访谈完，跑一遍 to-spec，把结论钉进文档。下次 AI 再眨巴着眼睛问你，你把规格甩给它，它自己就闭嘴了。

AI 想失忆，都失忆不了。

这套流水线我用了也有一阵子了。说真的，一开始我也老想偷懒，访谈完直接让 AI 写，跳过 to-spec。跳过两次，踩了两次坑之后，我学乖了。多花十分钟写一份规格，省下的是第二天重新访谈半小时。

对话是沙，文档是石。风一吹，沙就散了。石头立在那，十年后还在。

磨平一点信息差，哪怕只是你自己和昨天的自己之间，那一点。

## 快速回顾

- 流水线，grill 访谈 → to-spec（沉淀规格）→ to-tickets（拆工单）→ implement（写代码）
- 规格不是蓝图，它记录已确认的决策，不预测未来的需求，当预测用是滥用
- to-spec，把对话变成可回看、可评审的规格文档，发布到 issue tracker，只做沉淀不重访谈
- to-tickets，规格拆成带阻塞关系的工单，每个都是独立可验证的最小单元
- implement，按工单构建，边界处驱动 tdd，提交前 code-review，严守边界不扩大范围
- wayfinder，超大工作先探路，画调查工单地图，跟 Strangler Fig 同源
- 为什么拆，可审查、可复用、可验证，把大问题切成可控小问题
- 别当仪式，流程服务于项目，不是项目服务于流程
- 何时不要用，改动极小、探索性工作、只想快速试 AI
- 下一步，06 课，反馈回路，tdd 与 diagnosing-bugs，让 AI 写出的代码真的能跑
