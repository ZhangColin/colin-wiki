## retro 技能深度拆解：它修的不是代码

一个 45 行的技能文件，如何逼着 AI 承认：错误不在代码里，在环境里

你有没有过这种时刻：AI 把一个功能写完了，看着挺像回事，但心里总有点不踏实。后来你翻聊天记录才发现，它为一个函数的位置花了十几次工具调用，中间还搜错了两次目录。

大多数人这时候的反应是叹一口气，然后打开 AI 编辑器，在 CLAUDE.md 里再加一段。Matt Pocock 的 retro 技能专门反对这个动作。它的 SKILL.md 全文只有 45 行，做的事却一句话就能概括：它不改代码，它改下次运行时 AI 所处的那个环境。

## 01 它是什么，一个只会被手动调用的技能

先说清楚它在 mattpocock/skills 这个仓库里的位置。截至 2026 年 10 月 13 日，这个仓库的 GitHub 星标数是 289024，fork 数 24259，MIT 协议，从 2 月 3 日创建至今每天几乎都有提交。

仓库里的技能分成两类： **模型可调用** 的（任务对上了 AI 自己会拿来用）和 **只能手动调用** 的（你打字它才动）。retro 属于后者，而且这个限制是写死在配置里的硬约束。

> retro 的 frontmatter 里写着 `disable-model-invocation: true` ，配套的 openai.yaml 里还加了 `allow_implicit_invocation: false` 。AI 永远不会自作主张地给你复盘。

官方文档里给的理由很直白：一个跑得顺的会话没什么可学的，产出大多来自那些难熬的会话。而复盘本身需要人判断，强行自动执行只会攒下一堆没人需要的规则。

使用方式就是在一场跑砸了的会话之后，敲 `/retro` 。不指定会话就默认复盘当前这个，也可以指向本机会话日志里的任意一次历史会话。

## 02 七个类别，它到底在找什么

SKILL.md 的第三步列了七个检查类别，每一个后面都跟着一句 **Use when** 的触发条件。这个设计值得学：它不只说要看什么，还规定什么情况下才该看。

| 类别 | 查什么 | 什么时候该看 |
| --- | --- | --- |
| 导航 | 文件好不好找，有没有隐藏依赖，要不要加导航指针 | 会话花了很久才找到某个信息 |
| 自动化检查 | lint、类型、测试、pre-commit、CI，该不该补 | AI 犯了工具本可拦下的错，或仓库压根没护栏 |
| 编码规范 | 要不要给 reviewer 加新规则，或删掉旧规则 | reviewer agent 漏掉了某个错误 |
| 全局 AGENTS.md | 哪些引导指令该搬到规范或检查里 | AGENTS.md 特别大，仓库级或全局级都算 |
| 工具经济性 | 有没有烧 token 的笨办法，CLI 或 MCP 是否低效 | 出现了昂贵的工具调用 |
| 无效指令 | 引导文件里那些根本不改变行为的句子 | 引导文件臃肿难读 |
| 信息获取 | 能不能给 AI 更多入口，比如 tee 日志、只读权限 | 关键信息拿不到 |

这七个类别不是随便凑的，它们对应的是七种不同的失败形态：有的是找不到，有的是防不住，有的是规矩没地方放，有的是工具太笨，有的是信息进不来。

最后一步是按严重程度排序呈现给用户。它只提议，不动手，这一点在 SKILL.md 和官方文档里被反复强调。

## 03 全篇最锋利的那一刀

如果这份技能只记住一件事，那就是这一段：

> 所有工作都走两个阶段：实现和评审。实现 agent 承受最大的上下文压力，它要探索、写代码、调试失败。评审 agent 的上下文压力最小，它拿到的是一个 diff，不需要探索，往往也不需要写代码或调试。 **所以编码规范应该由评审 agent 来负责，而不是实现 agent。**

这段推理的力度在于它把一个凭经验的选择，替换成了结构性论证。实现 agent 的上下文窗口正被探索、编码、调试塞满，此时往里再塞十条规范，是往最拥堵的地方加车。评审 agent 拿到的上下文是干净的，它正需要一个评判依据。

顺着这个逻辑往下推，答案几乎是唯一的：新规则不进 AGENTS.md。因为 AGENTS.md 和 CLAUDE.md 会被推进每一个会话的上下文窗口，不管这次用不上也照推。这条技能对这件事的抵触程度超过其他一切主张。

它给出的文件分工也很清楚：AGENTS.md 和 CLAUDE.md 只放导航指针，极其节省地用；CODING\_STANDARDS.md 在评审阶段读，不是实现阶段读，一旦超过 1000 行就往文档目录里拆；文档是被指路才读的参考；技能则留给会被自动触发的内容。

## 04 机械违规 vs 判断题：这份技能的分水岭

在编码规范这一类里，SKILL.md 加了一段分类逻辑，这是整个技能最容易被忽略但最实用的部分：

**机械类违规** 指的是固定句法模式、禁用 API、import 形态、文件位置规则这类东西。这类违规直接做成确定性检查，没有讨论余地：写进仓库自己的 linter、加一个 pre-commit hook、或者加一个 CI job，选这个仓库语言和现有护栏下最省事的那个。原文的措辞是 **默认造检查，而不是写规则** 。

**判断题** 则是跨文件一致性、贴合周边风格这类没有任何护栏能替代的事。只有这些才配得上 CODING\_STANDARDS.md 里的一行字。

理由朴素得几乎粗暴：检查会失败，规范文件里的一句话不会。一个会失败的东西能挡住错误，一句话挡不住。

这段还有个更实用的推论被写进了自动化检查那一类： **先去读仓库自己的检查命令** ，也就是 package.json 或构建工具里的 lint 和 check 脚本、CI workflow。所以一个已经存在、但没接上或者已经悄悄失效的检查，那个发现应该是把它接上，而不是重新造一个。

最狠的一句留给了护栏缺失本身：一个既没有 pre-commit hook、也没有 CI 任务跑 lint 类型检查和测试的仓库，这件事本身就是一个发现项。没 lint 的仓库不是一个中性默认状态，而是一个长期存在的、错过的机会。

## 05 它的已知弱点，官方自己写出来了

这份技能文档少见地把自己的批评写进了正文。docs 页面的常见问题部分里，有三条自我批评比任何转述都准确。

**第一条是最要命的：会不会为了填满类别而编通用建议？** 官方直接把它称为对这份技能最有力的批评。原话是：任务一结束，AI 倾向于忘掉会话中段吃过的苦，然后编出通用建议来满足 retro 的各个类别。

解法是硬约束：每一条候选都必须来自会话自己的记录。这也带来了代价，它几乎不会给出无关建议，但可能对这一场会话的主题给得过重。所以文档给的验收标准是：凡是追溯不到具体时刻的候选，直接丢掉；严重程度排序也只是初稿，一个安静的昂贵错误完全可能排在一个吵闹的廉价错误后面。

**第二条是规则会只增不减。** 它能删东西，删引导文件里的无效指令，删本该属于规范或检查的引导内容，但它不审计上个月提出来的那些 lint 规则、hook 和 CI 任务。它只看一场会话，所以没法告诉你哪条规则现在触发太频繁，也没法告诉你它背后的 bug 已经不存在了。文档的结论很直接：修剪检查这件事还得你自己来，一条在好代码上频繁触发的规则，就是该删它的信号。

**第三条是长会话怎么办。** 默认复盘当前会话是最好的情况，因为挣扎还留在上下文窗口里。如果会话已经滑出了那个所谓智能区，就清空重开，然后指向日志里的那一场。

另外文档也顺手回答了一个常见困惑：没有任何技能会附带 CODING\_STANDARDS.md 这个文件，第一次有会话找到判断类规则时，retro 会提议创建，你接受之后 code-review 就会去读它。你已有的 CONTRIBUTING.md 之类同样管用。

## 06 它在整条链上的位置

retro 不是个孤立技能，它被放在主链的末尾，位置写得很清楚：

> `grill-with-docs → to-spec → to-tickets → implement → code-review → retro`

它最常调的其实是 code-review。新规范往哪放，答案是 code-review 的 Standards 轴读的地方。这也是为什么 retro 的规则归属逻辑不是纸上谈兵，它有实际的落点。

它和 improve-codebase-architecture 的区别在输入上：后者只需要代码，找的是代码结构本身的改进机会；retro 需要一段会话历史，改的是 AI 工作所处的环境。两个都用得上，谁也替代不了谁。

顺带一个细节：retro 的第一步是调用 writing-for-agents 技能拿写作风格指南，然后才去读会话记录。先学会怎么写，再去写，这个顺序说明作者清楚自己产出的东西也是给 AI 读的文件，得按那套标准写。

至于为什么 retro 不做记忆系统，文档的回答是：它不记录发生过什么，它改变环境，让错误没法再发生一次。

## 结语

retro 最有价值的可能不是那七个别类，而是它逼你接受的一个前提：AI 犯的错，大部分不是能力问题，是环境问题。你在 CLAUDE.md 里堆规则，是在给一个堵车的路口加红绿灯。

顺着这个思路往下，会碰到一个越来越清楚的方向：让 AI 的产出质量，靠仓库本身的护栏来保证，而不是靠某次会话里谁记得多。这件事今天靠人肉敲 retro 来启动，但方向是反过来的，从人去找错误，变成环境不让错误发生。
