## 前言

说实话，AI 太啰嗦这个坑，我自己写的时候都在叹气。

它用 20 个词解释本来 1 个词能说清的事，token 哗哗烧，你还得在它的废话里找重点。

解法只有一个文件， `CONTEXT.md` 。它不是随便写写就行的备忘录，是 Matt 整个技能集里「最酷的技巧」。

我先说一句，共享语言这个想法，不是我第一次见到。Eric Evans 的领域驱动设计里叫 ubiquitous language，我自己做领域建模也一直强调这个。Matt 的贡献在于，把它落成了一个给 AI 看的具体文件。所以这一课，我会一边讲它怎么建，一边讲它为什么在工程上是对的。

## 一、啰嗦的根因：AI 听不懂你的业务语言

先想一个问题，AI 为什么啰嗦？

不是它笨，是它没有你的领域词典。

你脑子里「满 1000 减 50」是一个清晰的概念，在 AI 眼里只是一串没有任何业务含义的文字。它猜不准，就只能绕着圈说话试探你。

解法不是让你写一堆文档，是一份不到 30 行的文件。

在 EShop 里，这个坑长这样：

```
你：修一下订单里那个"满 1000 减 50"退错钱的问题。
AI：好的，我理解的是订单金额满 1000 时应用 50 元减免，
    但退款时该减免可能没有被正确回滚……
    请问您说的"退错钱"具体是指退款金额少退了，
    还是订单金额本身算错了？另外……
```

AI 在干嘛？它在用 50 个字试探你，因为它不知道 EShop 里「满减」有自己的名字，不知道退款有专门的模块，更不知道这是不是历史遗留的已知问题。

现在换一种说法：

```
你：修复 AfterSaleOrder 里满减规则未正确回滚的问题。
AI：明白了，检查 FullReduction 在退款时的物化级联，开始定位。
```

三句话，AI 全懂。差别在哪？共享语言。前一种对话里，你们各说各话；后一种对话里，你们用同一本词典。

我年轻时做企业系统，最怕的就是这种「各说各话」。业务部门说「客户」，代码里叫 `Customer` ，数据表里叫 `T_CUST` ，一个词三个名字，每次沟通都在猜。AI 时代把这个老问题放大了，不是三个人猜，是每轮对话都在猜。共享语言，治的就是这个。

## 二、CONTEXT.md 是什么：项目的共享语言

Matt 的定义很直接， `CONTEXT.md` 是项目根目录下的一个文件，写清楚项目的术语、概念、模块关系，让 AI 一进来就能说「人话」。

它不是 README。README 讲「项目怎么跑起来」，给人类看； `CONTEXT.md` 讲「项目在说什么」，给 AI 看。它回答的是：

```
这个项目是干什么的？
领域里有哪些术语？代码里它们叫什么？
模块之间是什么关系？
有哪些约定是 AI 必须知道的？
```

有了它，AI 导航代码时认识每一个词，变量名、函数名、文件名都用同一套术语，token 花在思考上而不是猜词上。

这里有个类比，这份文件之于 AI，就像领域模型之于新的开发者。你给新人讲项目，不会从「数组和链表有什么区别」讲起，你会先讲「我们这里说的客户是下单的那个人，不是联系人」。 `CONTEXT.md` 干的就是这件事，只不过讲给 AI 听。

## 三、EShop 的第一份 CONTEXT.md

纸上谈兵没用，直接给 EShop 建。假设项目根目录是 `eshop/` ，新建 `CONTEXT.md` ：

```
# EShop 上下文文件

## 项目定位
EShop 是一个 Java Spring Boot 电商系统。核心业务闭环：用户浏览商品 → 下单 → 支付 → 库存扣减 → 发货 → 售后。技术栈：Spring Boot 3 + MyBatis-Plus + MySQL。

## 术语表（术语与代码同源）
| 术语 | 代码中的名字 | 含义 |
|------|-------------|------|
| SKU | Sku | 最小可售单元，一个商品可含多个 SKU（颜色、尺码） |
| 满减 | FullReduction | 订单金额达到阈值后整体减免的促销规则 |
| 物化级联 | MaterializationCascade | 促销规则逐层应用到订单行的计算逻辑 |
| 幂等 | Idempotent | 同一请求重复提交只生效一次 |
| 售后单 | AfterSaleOrder | 用户发起的退款或退货请求 |

## 模块地图
| 模块 | 关键类 | 职责 |
|------|--------|------|
| 订单 | OrderController / OrderService | 下单、查单、改单 |
| 支付 | PaymentController / PaymentService | 收单、回调、对账 |
| 用户 | UserController / UserService | 注册、登录、地址 |
| 售后 | AfterSaleOrderController / AfterSaleOrderService | 退款、退货 |

## 编码约定
- Controller 一律用 @RestController，返回 Result<{code, data, message}>
- 日志用 SLF4J，不用 Log4j
- Service 层是业务逻辑的唯一归宿，Controller 只做参数绑定与路由
```

这份文件不到 30 行，但它是 EShop 的「领域宪法」。AI 加载它之后：

- 说「满减」它知道是 `FullReduction`
- 说「售后」它知道去 `AfterSaleOrder*` 类里找
- 写 Controller 知道用 `@RestController` 和 `Result` 包装

这一份文件，把 AI 太啰嗦和代码风格跑偏两个坑同时填了。

## 四、怎么建：三种选择，从轻到重

CONTEXT.md 不是一次性写出来的，它会随项目生长。建它有三种选择，从轻到重。

### 选择一：手写初稿（最快）

花十分钟把上面 EShop 那套结构抄进你自己的项目，术语和模块地图先各写五条，够用就行。别追求一次写全，它会自己长。

### 选择二：用 domain-modeling 打磨（Matt 的推荐）

`domain-modeling` 这个技能专门干这个，它挑战你的术语、压力测试边界场景，逼你把「满减」和「优惠券叠加」之间的边界想清楚。你每确认一个术语， `CONTEXT.md` 就精一分。

### 选择三：用 grill-with-docs 边访谈边建（最重）

`grill-with-docs` 在做需求访谈的同时，会把访谈产出的领域模型写进文档，还会给难解释的设计决策记一条 ADR。适合项目初始化或者接手的项目，一次访谈把词典建起来。

我的建议是，新项目用选择一先跑起来，跑两周后觉得某些术语老是解释不清楚，再上选择二精修。选择三是锦上添花，不是必需品。

这也符合我的一个长期主张，文档应该是持续演化的，而不是一开始就写完的。 `CONTEXT.md` 也一样，先有个能用的初稿，让它跟着项目一起长。

## 五、术语一致性：别让语义扩散毁掉词典

CONTEXT.md 建好只是第一步。真正让共享语言生效的，是代码里的名字和术语表对得上。

反例长这样：

```
术语表里写着：售后单 AfterSaleOrder
代码里躺着：RefundRecord（退款记录）、ReturnRequest（退货请求）……

AI 看到术语表，再去代码里找人，名字对不上，词典就白建了。
```

这现象我有专门的名字，叫 semantic diffusion（语义扩散），一个概念在不同人、不同代码、不同文档里慢慢长出不同的名字，最后没人分得清谁在说哪个。

在 EShop 里，如果术语表定了「满减 = FullReduction」，那类名、字段名、方法名就统一叫 `fullReduction` ，别一会儿 `discount` 、一会儿 `promo` 。AI 认词的成本降到最低，思考的 token 才花得值。

防御语义扩散，靠的是纪律，改名要改全，新词先查表。AI 时代有个优势，AI 可以帮你扫一遍全库，找出「明明是一个东西却叫了三个名字」的地方，这正是它擅长的事。

## 六、算一笔账：共享语言省多少

最后给你一个具体的数。假设 EShop 一个「修退款」的任务：

**没有 CONTEXT.md** ：AI 先花 3 轮对话猜「退款」指什么，每轮 300 token 解释和试探，然后再花 2 轮确认范围。光对齐需求就烧掉约 2000 token。

**有 CONTEXT.md** ：AI 一眼看到「售后单 AfterSaleOrder」「物化级联 MaterializationCascade」，直接定位代码，0 轮试探，第一轮就开工。

省下的不只是钱。省下的是 AI 跑偏、返工、你审查错误代码的时间。

不过我得提醒一句，别把「token 数」当成衡量一切的标准。token 只是最容易量化的那部分，真正的收益是返工减少、代码一致、新 AI 上手快。这些很难量化，但不代表不存在。我常说 CannotMeasureProductivity，好东西不总能被数字证明，这不等于它不是好东西。

## 快速回顾

- 啰嗦的根因： AI 没有你的领域词典，只能绕圈试探
- 共享语言不新鲜： ubiquitous language 的老思想，Matt 落成了给 AI 看的具体文件
- CONTEXT.md： 项目根目录一份文件，写术语、概念、模块关系，给 AI 看
- EShop 实战： 术语表（术语与代码同源）+ 模块地图 + 编码约定，30 行搞定
- 三条建法： 手写初稿（快）→ domain-modeling 打磨（精）→ grill-with-docs 边访谈边建（重）
- 语义扩散是敌人： 一个词全项目通用，名字对不上词典就白建
- 收益与边界： 省 token、省返工；但别拿 token 当唯一标准
- 下一步： 04 课，用 grill-me 访谈 EShop 的下单需求，让 AI 动手前先把决策树问清楚
