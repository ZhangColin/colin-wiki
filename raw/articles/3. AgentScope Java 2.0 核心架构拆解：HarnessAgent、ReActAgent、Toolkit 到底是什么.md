![[Image 107.webp|3. AgentScope Java 2.0 核心架构拆解：HarnessAgent、ReActAgent、Toolkit 到底是什么]]

在 Web 项目里，Agent 入口通常会落到这一行：

java

devAgent.streamEvents(request.message(), context)

这行代码不只是调用模型。遇到需要工具的任务，执行主链路是：

text

Controller

\-> Service

\-> HarnessAgent

\-> ReActAgent

\-> Model 流式返回 ChatResponse

\-> 响应内容中出现 ToolUseBlock

\-> Toolkit 执行工具

\-> ToolResultBlock 写回上下文

\-> ReActAgent 再调模型

\-> 生成最终回答

`RuntimeContext` 会把 `userId` 、 `sessionId` 带进执行链路，用来定位会话状态； `ReActAgent` 通过 `AgentStateStore` 加载和保存对应的 `AgentState` ；模型调用、工具执行和最终结果会持续产生 `AgentEvent` ，再由 Web 层转换成 SSE。

其中最容易混的是三层：

text

HarnessAgent：应用入口和工程化包装

ReActAgent：推理与行动循环

Toolkit：工具注册、Schema 暴露和工具执行

理解这三层，就不会一遇到 Agent 行为不符合预期，就只盯着 Prompt 改。

## 一、HarnessAgent：外面这一层管工程问题

`HarnessAgent` 是 AgentScope Java 2.0 提供的高层入口。

它内部持有一个 `ReActAgent` ：

java

public class HarnessAgent implements Agent, AutoCloseable {

private final ReActAgent delegate;

}

Builder 里也是同一条线：

java

private final ReActAgent.Builder inner = ReActAgent.builder();

text

HarnessAgent 不是另一套推理核心。

它是在 ReActAgent 外面加了一层运行时包装。

调用 `streamEvents(...)` 时， `HarnessAgent` 会先处理运行上下文，再把请求交给内部的 `delegate` ：

java

public Flux\<AgentEvent> streamEvents(List\<Msg> msgs, RuntimeContext ctx) {

RuntimeContext effective =

ensureSessionDefaults(ctx!= null? ctx: RuntimeContext.empty());

return wrappedStreamEvents(effective,

() -> delegate.streamEvents(msgs, effective));

}

text

ensureSessionDefaults：补默认 sessionId，并注入 Harness 运行上下文

wrappedStreamEvents：在配置沙箱时管理调用前后的沙箱生命周期

delegate.streamEvents：进入 ReActAgent 核心循环

`HarnessAgent` 还在 `ReActAgent` 外面组织 workspace、filesystem、sandbox、subagent、skill、plan-mode 和 MCP 等能力。

text

ReActAgent 负责推理、工具执行和迭代控制。

HarnessAgent 负责组装工作区、记忆、沙箱、子 Agent、技能及相关中间件。

这些能力不必一次全打开。排查主链路时，可以先把文件系统、Shell、记忆、子 Agent、动态 Skill 关掉，把链路收窄成：

text

Web 请求

\-> HarnessAgent

\-> ReActAgent

\-> Model

\-> AgentEvent

主链路稳定后，再逐步增加工具、配置权限规则，并接入 Workspace 和持久化状态。

## 二、ReActAgent：里面这一层跑推理-行动循环

`ReActAgent` 是 AgentScope Java 的核心执行器。

这里的 ReAct，不要理解成“框架会暴露模型的完整思维链”。更准确地说，它描述的是一种运行节奏：

text

模型判断下一步

\-> 需要工具就发起工具调用

\-> 应用执行工具

\-> 工具结果回到上下文

\-> 模型继续判断

这条链路大致对应两个方法：

text

reasoning(...)：调用模型，处理模型回复

acting(...)：执行工具，把工具结果写回上下文

`ReActAgent` 不绑定某一家模型服务。底层可以是 DeepSeek、DashScope、OpenAI 兼容接口，也可以是别的模型实现。它依赖的是 `Model` 接口：

java

Flux\<ChatResponse> stream(

List\<Msg> messages,

List\<ToolSchema> tools,

GenerateOptions options);

模型接收消息和工具 Schema，返回 `ChatResponse` 流。需要调用工具时， `ToolUseBlock` 会出现在响应内容里。

接入工具后，路径会展开：

text

用户消息

\-> reasoning

\-> Model.stream(...) 返回 ChatResponse 流

\-> 响应内容中出现 ToolUseBlock

\-> acting

\-> 权限判断

\-> Toolkit 执行工具

\-> ToolResultBlock 写回上下文

\-> 下一轮 reasoning

\-> 最终回答

举个具体例子。

用户问：

text

这个项目用了哪个 Java 版本，启动类在哪里？

如果应用提前在 `Toolkit` 里注册了 `read_pom` 和 `find_main_class` 这两个 Java 工具，模型看到的就不只是 Prompt，还有工具名称、描述和参数 Schema。

text

模型先判断：需要查 pom.xml 和启动类

\-> 生成 read\_pom / find\_main\_class 调用请求

\-> Toolkit 执行 Java 方法

\-> 返回 pom.xml 内容和启动类路径

\-> 模型基于工具结果组织回答

回答不对，不一定是模型不会答；也可能是工具没暴露、Schema 不清楚、权限拒绝了，或者工具结果没回到上下文。

## 三、Toolkit：模型只提请求，应用侧执行工具

`Toolkit` 负责工具。

它做的事情包括：

text

注册工具

生成工具 Schema

管理工具分组

转换工具参数

执行工具方法

包装工具结果

比如你注册一个 Java 工具：

java

agent.getToolkit().registerTool(projectInfoTools);

里面的方法可能长这样：

java

@Tool(

name = "read\_pom",

description = "读取当前 Maven 项目的 pom.xml",

readOnly = true)

public String readPom(

@ToolParam(

name = "max\_chars",

description = "最多返回多少个字符",

required = false)

Integer maxChars) {

// read pom.xml

}

注册以后， `Toolkit` 会把它变成模型能理解的工具描述。

模型和应用的边界是：

text

模型不会自己执行 Java 方法。

模型只是根据工具 Schema 生成工具调用请求。

工具执行发生在应用侧。

比如模型可能生成：

json

{

"name": "read\_pom",

"arguments": {

"max\_chars": 4000

}

}

这一步还没有读取文件。

读取 `pom.xml` ，发生在 `Toolkit` 执行工具的时候。

text

在工具调用阶段，模型负责选择工具和生成参数。

应用负责校验、权限、执行和返回结果。

## 四、RuntimeContext 和 AgentState：一个标记调用，一个保存进度

这两个对象别混：

text

RuntimeContext：本次调用携带的上下文

AgentState：这段会话的执行状态

`RuntimeContext` 是一次调用的上下文，里面带着 `userId` 、 `sessionId` 等信息。 `AgentState` 保存的是会话运行状态。

`AgentState` 保存会话标识、消息上下文、摘要、迭代次数，以及权限、工具、任务和 Plan Mode 等状态。下面是其中一部分字段：

java

private String summary;

private final List\<Msg> context;

private int curIter;

private PermissionContextState permissionContext;

private final ToolContextState toolContext;

private final TaskContextState tasksContext;

状态槽位由 `userId` 和 `sessionId` 定位：

java

String sid = ctx!= null? ctx.getSessionId(): null;

String uid = ctx!= null? ctx.getUserId(): null;

String slot = slotKey(uid, sid);

同一个 Agent 实例可以服务多个会话，关键是每次调用传对上下文。 `userId` 更建议从登录态或网关上下文里取，不要完全信任前端传来的用户标识。

如果使用 `InMemoryAgentStateStore` ，进程一重启，状态就没了，多实例之间也不会共享。单机持久化可以使用 `JsonFileAgentStateStore` ；多实例部署需要 Redis 等分布式 `AgentStateStore` 。

## 五、AgentEvent：把过程流出来，而不是只拿答案

`streamEvents()` 返回的是：

java

Flux\<AgentEvent>

这不是普通字符串流。

AgentScope Java 2.0 会把执行过程拆成事件。一次带工具的调用里，常见事件包括：

text

AgentStartEvent

ModelCallStartEvent

TextBlockDeltaEvent

ToolCallStartEvent

ToolCallEndEvent

ToolResultStartEvent

ToolResultEndEvent

AgentResultEvent

AgentEndEvent

需要人工确认时，还会出现：

text

RequireUserConfirmEvent

RequestStopEvent

所以前端不要只把它当“打字机效果”。原生事件可以转成业务侧 SSE 事件：

text

MESSAGE：追加文本

TOOL\_CALL\_START：显示正在调用哪个工具

TOOL\_RESULT\_END：显示工具执行状态

REQUIRE\_USER\_CONFIRM：弹确认框

AGENT\_RESULT：保存最终结果

DONE：关闭 loading

## 六、排查问题，先看是哪一层

Agent 项目一复杂，最怕的不是报错，而是不知道该查哪。

可以按这张表先定位：

| 现象 | 先看哪一层 |
| --- | --- |
| 接口参数不对，直接 400 | Controller / DTO |
| 模型鉴权失败 | Model 配置 |
| 模型一直不调工具 | Prompt、工具 Schema、Toolkit 注册 |
| 工具调用参数不对 | 工具 Schema、参数描述、ToolParam |
| 工具执行报错 | Toolkit、工具实现、参数转换 |
| 工具被拒绝 | PermissionContextState、PermissionEngine、ToolBase#checkPermissions |
| 多用户上下文串了 | RuntimeContext、AgentStateStore |
| 重启后会话丢失 | 是否仍使用 InMemoryAgentStateStore |
| 后端有事件，前端看不到状态 | AgentEvent 到 SSE 的映射 |

分清层以后，就不用一遇到问题就改 Prompt。

## 写在最后

回到开头那行：

java

devAgent.streamEvents(request.message(), context)

它背后不是一次简单的模型调用。

更准确地说，它会进入这样一套结构：

text

HarnessAgent 负责入口和工程设施

ReActAgent 负责推理-行动循环

Model 负责对接模型服务

Toolkit 负责工具注册与执行

RuntimeContext 标记本次调用

AgentState 保存会话进度

AgentEvent 把执行过程流出来

`HarnessAgent` 和 `ReActAgent` ，可以理解为整车和发动机的关系：

text

ReActAgent 像发动机，负责真正执行推理和工具调用。

HarnessAgent 像整辆车，在外面装上工作区、记忆、沙箱、子 Agent 和技能等工程能力，再由内部的 ReActAgent 驱动任务。
