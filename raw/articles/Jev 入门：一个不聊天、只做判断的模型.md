## Jev 入门：一个不聊天、只做判断的模型

> 当需要模型进行判断时，多数人的第一反应是打开聊天窗口，撰写一段提示词，再设法将返回内容解析为可用字段；新发布的 Jev 则采取了另一条路径：它不参与对话，仅将判断结果以数据形式返回。真正的差异在于调用频次，此类判断往往需要反复执行，而单次成本一两分钱的方案与单次耗时几毫秒的方案，所能覆盖的落地场景相去甚远。
> 
> 文档与示例代码已附于文章底部，请自行取用。

## 01 那些写不进 if-else 的判断：AI 判断模型能做什么

![[Image 163.png|Jev 的定义与第一个类比]]

先看一个例子。假设一位商家经营网店，想给买三件及以上商品的顾客免运费。这个条件在代码里写起来很直接，数一下件数，大于等于三就免运费。

再换一个需求，把听起来不满的顾客留言挑出来。这个条件该怎么写？

可以去找关键词，麻烦在于顾客未必按商家准备的词表说话。留言里可能只有一句「我已经联系你们三次了，还在等」，整句没有出现「不满」两个字，意思却谁都能看出来。

Jev 就出现在这里。把留言交给它，问一句这位顾客听起来是否不满，它看一眼内容，零点几秒内给出判断。给出的概括是，把它想成一个 **聪明的 if 语句** 。

Jev 是 TypeSafe 公司的模型，它的发布帖在社交平台上已经有了超过三千万浏览。官方给它的定义需要拆开读：

> 一个 system one 模型，做快速、结构化、软件可以直接使用的判断。

看到别人讨论 **Jev** 时，人们最先冒出的念头多半是同一个： **我是不是也该用上它？** 但要判断这件事，得先弄明白： **Jev 到底能解决什么问题，它适不适合放进自己的工作流。**

- 它究竟在计算什么？
- 它需要多少成本？
- 和聊天模型差在哪里?
- 什么时候不该用?

这几件事恰好也是技术选型时该优先弄清楚的。

![[Image 218.webp|名字与概念的两处出处]]

定义里有两处出处值得交代：

**system one** 出自丹尼尔·卡尼曼的《思考，快与慢》。书里把人的思考分成两套：一套是快速的直觉判断；一套是更慢的审慎推理。TypeSafe 借的是前一套，用来指那种在软件内部做快速判断的模型。

**Jev 这个名字** 来自威廉·斯坦利·杰文斯。这位经济学家注意到蒸汽机身上一件反常识的事，蒸汽机效率变高，照理说该少烧煤，运行成本降下来之后人们反而用得更多，煤耗总量跟着上升。

这就是杰文斯悖论，英文写作 Jevons paradox。

TypeSafe 把它当作对 AI 的预期，判断一旦便宜到可以忽略，它就会被塞进以前算不过账的场景里。

## 02 判断模型为什么更快更便宜：与聊天模型的本质差别

![[Image 219.webp|官方定义的后半句]]

做快速、结构化、软件可以直接使用的判断，这个半句里的三个词各自都有具体所指：

**快：** 指等判断的时间短，TypeSafe 公布的端到端响应时间是 **70 到 500 毫秒** 。

**结构化 **：**** 指返回数据，而不是像聊天那样给出一句句话和一段段文字。

**软件可以直接使用 **：**** 说的是嵌进应用里使用，这正是它的设计目标。回到那条留言，可以让 Jev 判断顾客是否不满，再由应用拿这个结果把留言标记给客服：

> 判断由它做，接下来发生什么由程序定。

对写代码的人来说，返回数据这一点比速度更实用。成段的文字要先解析、再校验，格式对不上还得重试；而返回概率与选项则可以直接跳过解析，进入业务分支。

读到这里，难免会冒出一个质疑：OpenAI 和 Claude 的模型不也能做判断，不也能按要求返回结构化数据吗？

能，官方演示里也承认了这一点。差别在于设计目标。GPT 和 Claude 这类模型除了判断，还要给顾客写回复、解释概念、生成代码；而 Jev 只做判断这一件事，它不生成回复，也不解释自己的答案。

取舍带来的结果十分明确：由于无需逐 token 生成回复，答案的概率便可以并行计算——快与便宜，皆源于此。token 是模型处理文本的最小单位，一个汉字通常对应一到两个 token。。

![[Image 220.webp|同一任务的双指标对照]] ![[Image 221.webp|聊天模型与判断模型的设计目标差异]]

同一件事，两边的数字差得很远。交给 GPT-5.6 Terra 要 **8.6 秒** ，交给 Jev 只要 **114 毫秒** 。成本上前者约 1.4 美分，后者不到百分之一美分，只有前者的约 **一百七十分之一** ：

| 对照维度 | GPT-5.6 Terra | Jev |
| --- | --- | --- |
| 响应时间 | 8.6 秒 | 114 毫秒 |
| 单次成本 | 约 1.4 美分 | 不到百分之一美分 |
| 成本倍数 | 基准 | 约前者的 1/170 |
| 是否生成回复 | 给顾客写回复、解释概念、生成代码 | 不生成回复，也不解释自己的答案 |

## 03 定价与成本换算：一笔能算清的账

![[Image 222.webp|定价与换算尺度]]

现价是每百万输入 token 收 **4.2 美分** ，也就是每十亿输入 token 收 **42 美元** 。输出 token 完全不计费，只为发进去的内容付钱：

| 计费项 | 数值 |
| --- | --- |
| 输入 token | 每百万 4.2 美分，即每十亿 42 美元 |
| 输出 token | 完全不计费 |
| 换算尺度 | 每条留言加问题约 500 输入 token，1 美元约检查 47000 条 |

换成日常尺度更容易判断：

- 每天收到一万条顾客留言，逐条检查是否不满
- 每条留言加上问题，约 500 个输入 token
- 按这个量算，1 美元可以检查 47000 条

留言长短和问题复杂程度当然会变，换算出来的量级不会变：

> 把每一条进来的留言都过一遍，花在判断上的钱不多。

这也解释了它为什么值得被大量调用。判断这类事情过去用生成模型做，成本高到只能挑重点场景，能省则省。单价降到这个量级之后，原本因为算不过账而放弃的场景重新变得可行，与杰文斯悖论里那句预期对上了。

## 04 输入结构：一份 state 加一组问题

![[Image 223.webp|输入结构，一份 state 加一组问题]]

一次请求要给 Jev 两样东西：

- 想让它看的信息
- 想让它回答的问题

TypeSafe 管前者叫 state，它就是交给模型去看的那份材料，可以是纯文本、一个 JSON 对象，或者一个数组。那条留言「我已经联系你们三次了，还在等」，就是交给 Jev 的 state。

问题部分可以给一个，也可以给多个。每个问题还要根据期望的答案形式，选定一种问题类型。可选的一共三种。

![[Image 224.webp|三种问题类型]]

| 问题类型 | 用在什么判断上 | 返回什么 |
| --- | --- | --- |
| Noul | 是非判断 | 答案为「是」的概率，取值在 0 和 1 之间 |
| choice | 从给定的选项里挑一个 | 选中项，以及所有选项各自的概率 |
| score | 判断某个东西落在刻度上的什么位置 | 得分、各级概率，另附把每一级对应回描述的说明 |

第一种是 **Noul** ，用来做是非判断。它不返回 true 或 false，而是返回「是」的概率，取值在 0 和 1 之间。假设返回 0.95，表示它估计「是」的概率是 95%。

取值越接近 0，越说明它倾向于给出否定判断；取值在 **0.5 附近** ，说明它没有明显偏向哪一边。有一个地方容易读错，低值不代表模型拿不准，它代表模型相当确定这条留言不属于不满。

第二种是 **choice** ，用来从给定的选项里挑一个。想知道顾客这次联系是为了什么，可以给四个选项，分别是询问进展、要求退款、要求换货，以及其他。Jev 挑出其中一个，同时返回所有选项各自的概率。

关键在于选项由调用方定义， **它必须从这份列表里选** 。「其他」这一项不能省，那些归不进前三类的留言需要有个去处。

第三种是 **score** ，用来判断某个东西落在刻度上的什么位置。前面已经问过顾客是否不满，如果还想知道不满到什么程度，可以给一个三级刻度，从提出请求但没有表达不满，到表达不满意，再到表达强烈愤怒。

注意这里写的是每一级的含义，比起只写一句从一到十分，它给了模型更明确的参照。

刻度从 0 起算，得分是各级概率的加权平均，所以结果可以落在两级之间。一级和二级概率相等时，得分就是 1.5。

这三个问题不需要分成三次请求。它们看的是同一份 state，可以放在同一次调用里并行评估。并行评估里的「独立」有个明确含义：

> 一个问题读不到另一个问题的答案，每个问题都要能凭 state 自己成立。

落到工程上，合并调用既省下 token 开销，也省下网络往返。

## 05 概率与置信度：什么情况下必须留给人复核

![[Image 225.webp|输出结构与置信度]]

响应里每个答案都对得上请求里给问题起的名字。Noul 返回答案为「是」的概率，choice 返回选中项和全部选项的概率，score 返回得分、各级概率，另附一份说明，把每一级对应回它的描述。

给出答案，并不等于答案正确。Jev 仍然可能误读留言。所以 choice 和 score 还会额外返回一个 confidence 值，它根据概率的分布算出，用来帮助决定应用该直接采纳这个答案，还是留给人复核。 **Noul 没有单独的置信度字段，要看它的概率在「是」和「否」上偏向得有多强。**

| 问题类型 | 置信度字段 | 怎么判断能不能直接采纳 |
| --- | --- | --- |
| Noul | 没有单独的置信度字段 | 看概率在「是」和「否」上偏向得有多强 |
| choice | 额外返回一个 confidence 值 | 根据概率的分布算出，决定直接采纳还是留给人复核 |
| score | 额外返回一个 confidence 值 | 根据概率的分布算出，决定直接采纳还是留给人复核 |

> 置信度不是准确率的保证。

多高的置信度算够用，得拿自己的样本试过才知道。响应里还会附带处理这次请求的模型版本，以及用掉的 token 数量。

把阈值设在哪里，等于决定哪些判断可以自动放行、哪些必须有人过目。这件事没有通用答案，样本里混进多少模棱两可的留言，阈值就该往哪边偏。

## 06 上手实操：先在 Playground 跑一次，再写 TypeScript 代码

![[Image 226.webp|在 Playground 里试跑一次请求]]

入口有两条。先去 TypeSafe 官网，Jev 目前处于 Early Access，没有权限要先加入等待名单；也可以走 Vercel AI Gateway，9 月 23 日之前免费。Early Access 指正式开放前的限量试用。拿到权限后登录控制台，可以在 Playground 里试，也可以取一个 API key 用在自己的代码里。Playground 是控制台里的在线试用页面，不用建项目就能直接发请求：

| 上手路径 | 入口 | 适合做什么 |
| --- | --- | --- |
| Playground | 登录 TypeSafe 控制台 | 不用建项目就能试跑，也能一次加好几个问题，把答案摆在一起看 |
| 代码 | 取一个 API key，装 `@typesafe-ai/sdk` | 接进真实业务 |

写代码之前先在 Playground 里跑一次。上方区域填 state，下方区域填问题。state 写成 JSON，带一个 `message` 字段，值是那条顾客留言。问题类型选 Noul，内容是这条留言是否表达了不满。运行的结果是 92% true，这个值越接近 1，就说明 Jev 越认为顾客听起来不满，响应时间也一并显示出来，单位是毫秒。

Playground 里也能一次加好几个问题，把答案摆在一起看。不过要接进真实业务，还是得走代码。下面这段代码用 TypeScript 写，它是给 JavaScript 补上类型检查的语言，写完先做类型检查，再交给运行时执行。

![[Image 164.png|TypeScript 实操，demo.ts 与 all-questions.ts]]

从代码里重发同一条请求，项目结构需要几样东西。装 `@typesafe-ai/sdk` ，配 TSX 和 Node.js 的类型定义，让 TypeScript 文件能直接运行，用 ES modules 好在顶层直接 await 请求，密钥放 `.env` ：

> 示例 env 文件里那个 key 要记得换成自己的，这是最容易被照抄漏掉的一步。

`demo.ts` 里的流程是这样：

1. 导入 TypeSafe 的 client 和 Noul 辅助函数
2. 检查 API key 可用，创建一个新的 client
3. 定义 state，一个 `message` 属性装着那条留言
4. 调用 `client.system1` ，把 state 和问题传进去

问题名取作 `is frustrated` ，这个名字就是之后在响应里找答案用的键。 `noul` 里的文本才是 Jev 真正评估的那句话，并且指向 state 里的 `message` 字段。执行 `npm run demo` ，几乎瞬间返回结果。

模型是 Jev 1.13.0， `answers` 下面是 `is frustrated` ， `noul` 的值是 0.94，用量是输入 token 约 292、输出 token 23。

把留言换成「谢谢更新，现在一切正常」，问题不动，再跑一次，结果变成 0.03，意思是否定的。耗时依然不到一秒。

第二个文件 `all-questions.ts` 把三种类型放进同一次请求。它用的还是原来那条留言， `is frustrated` 问题照旧，另外加了一个 choice 问主要诉求，选项是询问进展、退款、换货、其他，再加一个 score 问不满程度，刻度就是前面那三级。

仍然只发一次调用，因为三个问题共用同一份 state。

执行 `npm run all` 之后逐个看答案：

- `request type`
	是 choice 类型，选中 update，置信度 0.99，概率分布里 update 占 0.99，其他是 0.01
- `is frustrated`
	是 Noul 类型，给出的概率与上一次一致
- 不满程度那一问得到 score 1.02，置信度 0.97，概率是 0.98 和 0.02

1.02 落在 1 和 2 之间，意思是顾客表达了不满意但没有到强烈愤怒，还稍微往愤怒那一侧偏了一点。三个问题问完，耗时还是不到一秒，用量显示在响应底部。

最后一步是把判断接进业务逻辑。演示代码设了一个 0.8 的复核阈值，拿 `answers.is frustrated.noul` 和它比较，超过就把这条留言标记给客服复核，终端里能看到这条输出。0.8 只是为了演示，实际应用要拿一批有代表性的留言试过、看过结果再定这个数。

## 07 适用场景对比：什么该交给它，什么不该

![[Image 227.webp|该用与不该用 Jev 的场合]] ![[Image 165.png|适用与不适用]]

适合它的任务有个共同特征，都是判断，而不是生成：

- 给客户请求做路由
- 给大批文档分类
- 判断一段文字是否支撑某个结论
- 决定某个任务该交给哪个模型
- 用在游戏或界面里需要即时决策的地方

TypeSafe 的文档里另有一份更长的清单，搜索与检索、科学发现、模型路由、大模型护栏、语义化代码检查、招聘、线索挖掘、客户支持、保险理赔、金融犯罪、广告、游戏都在其中，还按类别给了示例任务。做技术选型的时候值得翻一翻。

不该用它的场景同样清楚。要写回复、要总结文章、要生成代码，这些任务需要的是生成文本的模型，Jev 可以判断喂进去的信息，但不会替调用方把结果写出来。另有一类判断本来就不需要模型。 **答案能在代码里精确算出来的，就用代码算。** 算数、计数、比较日期，以及前面那个购物车里是否满三件的条件，都属于这一类：

| 场合 | 具体例子 |
| --- | --- |
| 适合交给 Jev | 客户请求路由、大批文档分类、判断一段文字是否支撑某个结论、模型选型、游戏或界面里的即时决策 |
| 不该用它 | 写回复、总结文章、生成代码，这些需要能生成文本的模型 |
| 不该用任何模型 | 算数、计数、比较日期、购物车是否满三件，答案能在代码里精确算出来 |

如果要把判据压成一句话，可以这样记：

- 手上有一个判断要做
- 调用方描述得出可能的答案，选项列得出，或者每一级的判据写得下
- 速度或者重复调用对业务重要

三条都占，这个任务就值得试试 Jev。

至此，Jev 的轮廓已然清晰，且相当窄：给它一份 state 和一组问题，它返回结构化答案，三种类型分别对应是非、选项与刻度。它之所以快、之所以便宜，根源在于无需逐 token 生成回复；接入路径亦不长，先在 Playground 里跑通，再照搬至 TypeScript 即可。。

Jev 所划出的那条线，比它自身的功能更值得玩味。过去几年，凡是模型可以插手之处，我们皆以同一个模型应对，判断、生成与解释混杂在同一次调用之中。Jev 则将判断单独抽出，做成一个更窄、更快、更便宜的东西，其余部分交还给代码：

> 模型变窄，反而更好用，这才是这条线带来的变化。

若要动手尝试，建议从应用中最小的一处判断入手，例如为一条客服留言标注是否不满，再用自己积累的真实样本跑一遍，观察概率分布落在何处。。
