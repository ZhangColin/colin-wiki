## 场景：乐乐账本里，冒出全家的工资

那天艳姐喊我，语气不对：「老谭，你过来看。我切到乐乐的零花钱账本看报表，里面居然有一笔 **工资收入 12000** ——那是咱家的钱，怎么跑乐乐账里去了？」

我心里一沉。零花钱刚上线就出这档子事，这不就是账本串了吗？

但这次不一样——前面 22 篇技能不是白学的。我没急着改代码，而是把调试类的技能全部摆上桌：

- systematic-debugging： 搭排查的流程（复现 → 假设 → 验证 → 根因）；
- root-cause-tracing： 顺着因果链追根因；
- verification-before-completion： 修完验证，防回归。

三个技能组合上阵，这就是组合实战的意义—— **不是再用一个技能，而是让技能们协同。**

## 第一步：复现——把"串账本"钉死在证据上

先复现。现象：“乐乐账本下，报表页显示工资收入 12000”。

**复现的第一步是分清前后端。** 后端是接口，先 curl 单独验证，把前端摘出去：

```
# 乐乐账本（ownerId=2）的月度报表
curl -H "X-User-Id: 2" "http://localhost:8080/api/reports/monthly?month=2026-08"
```

后端返回什么？乐乐的账只有两笔（文具 45、零食 12），报表里 **根本没有工资** ——后端是对的。

那问题就在前端。复现得更精确一点： **切到乐乐账本，报表页显示的还是家庭的数据。**

## 第二步：假设——列全病因

前后端一拆，嫌疑集中在前端。列假设：

- 假设 A：前端切账本后，报表没重新拉数据——显示的还是上一个账本（家庭）的旧数据；
- 假设 B：前端拉数据时没带 `X-User-Id` ——后端当成了默认的 1（家庭）；
- 假设 C：后端接口缓存了——第一次查家庭的结果被缓存，第二次查乐乐还是旧的。

三条假设，逐个验证。

## 第三步：验证——逐个排除

**验证 C** ：我们的接口没有缓存层，Spring Boot 默认不缓存。而且刚才 curl 乐乐账本返回正确——后端没缓存。C 排除。

**验证 B** ：看前端的请求封装 `request.js` —— `ownerId` 传入就自动带 `X-User-Id` 头。切账本时 `ownerId.value` 确实是 2。打开浏览器 DevTools 的 Network，切账本，看请求头—— `X-User-Id: 2` ，带对了。B 排除。

**验证 A** ：看报表页组件，问题浮出水面——

`watch([month], load)` —— **它只在月份变化时重拉数据，账本（ `ownerId` ）变了，根本没触发 `load` 。** 所以切到乐乐账本，页面还留着上一次（家庭）拉回来的数据。数据不是"串了账本"，是 **前端根本没重新请求** ——你看到的是家庭账本的旧页面。

**根因锁定：报表页的 `watch` 漏了 `ownerId` 依赖。**

修法就一行——把 `ownerId` 加进 watch 依赖：

修完， **回到复现那一步验证** ：切到乐乐账本，报表页立刻重拉，只显示乐乐的两笔支出，工资消失。✓

再补一条 **防回归测试** ——这个 bug 的本质是"账本切换后数据要刷新"，用前端测试钉死：

```
import { describe, expect, it, vi } from 'vitest'
import { useLedger, LEDGER_FAMILY, LEDGER_KID } from './useLedger'
import { reports } from './api/request'

it('切换账本后触发重新拉取', async () => {
  const load = vi.fn()
  const { ownerId } = useLedger()
  // 模拟"账本变化触发 load"的链路
  ownerId.value = LEDGER_KID.id
  // 断言：依赖账本的加载逻辑会被触发（此处示意断言）
  expect(ownerId.value).toBe(2)
  expect(load).toBeDefined()
})
```

> 严格说， `watch([month, ownerId], load)` 的"切账本就重拉"这个行为，最好用一个真实的组件挂载测试来断言"拉取函数在账本变化时被调用"。上面是示意骨架——真实工程里把它写成一个组件测试，断言 `reports.monthly` 被重新调用。

最后按 `verification-before-completion` ： `npm test` 绿、浏览器把"切账本 → 报表刷新 → 数据正确"走一遍，收工。

## 这次排查，三个技能各干了什么

| 技能 | 在本次排查里的角色 |
| --- | --- |
| systematic-debugging | 搭流程：复现 → 假设 → 验证 → 根因，步步有证据 |
| root-cause-tracing | 顺着"切账本 → 页面没刷新"的因果链，追到 `watch` 漏依赖 |
| verification-before-completion | 修完回"复现"验证，加防回归测试，才宣布完成 |

**组合实战的价值就在这：单靠哪个技能都不够——流程让你不走弯路，追踪让你挖到根子，验证让你不再犯第二次。**

## 注意事项

1. 前后端联查，先 curl 后端分而治之。 报表串账本，先单独验后端接口，把前端摘出去。一锅粥地看，只会越看越乱。
2. “数据不对"不一定是"数据错了”，可能是"没刷新"。 这次就是典型的"看到旧数据"——先查请求有没有真的发出去，再看返回对不对。
3. `watch` 漏依赖是前端串数据的头号嫌疑。 页面依赖账本/筛选条件，就要把依赖全写进 `watch`
	。写一半，就是这次这个 bug。
4. 修完回复现验证 + 加防回归。 当初怎么复现的，修完怎么验证；再写个测试，让 bug 回不来。
