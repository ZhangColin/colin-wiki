## 前文回顾

上一篇 [10｜superpowers/using-git-worktrees 前后端并行开发不打架](https://mp.weixin.qq.com/s?__biz=MzYyMTQ4MDI1OA==&mid=2247484291&idx=1&sn=77c53d602d4fc095028a745be917f750&scene=21#wechat_redirect) 我们用 worktree 让前后端并行开发不打架。报表前端、报表后端两个分支都干完，各自提交了。

老王的问题很实际： **“合回来是合回来了，但你怎么知道合得对？”**

## 场景：合之前，先问三个问题

很多人干完活，一拍脑袋就 `git merge` 了。结果合进去的是个半成品，甚至把主线的测试弄红。

`finishing-a-development-branch` （分支收尾）教的是： **合之前，先想清楚这个分支该不该合、怎么合。**

它给分支定了三种结局：

1. 合（merge）——活干完了，测试绿，验收通过；
2. 修（fix）——方向对但有瑕疵，修好再合；
3. 弃（discard）——方向错了，白干了，直接删。

判断依据就三样： **代码审查、测试结果、与验收的对齐** 。今天用「报表后端接口」这个分支，把完整收尾走一遍。

## 怎么用：收尾四步走

### 第一步：先自检，再动合并

合之前，先在自己分支上把"该验证的"验证一遍。测试是硬门槛—— **测试不过的分支，没有资格进主线** ：

```
cd ../hl-be-report          # 报表接口分支的工作区
"$MAVEN_HOME/bin/mvn" test  # 后端测试必须全绿
```

全绿了，再看一眼自己到底改了什么—— **别连自己改了啥都不知道就往主线里塞** ：

```
git log --oneline main..report-backend   # 这个分支比主线多了哪些提交
git diff main...report-backend           # 总的差异长什么样
```

`git diff main...report-backend` 把"这个分支相对主线的全部改动"摊开给你看。这一步，是把"我好像改了啥"变成"我清清楚楚知道改了啥"。

### 第二步：判断——合、修、还是弃？

对着差异，问自己三个问题：

- 代码审查： 这段代码我能讲明白吗？有没有看不懂的、没道理的改动？
- 测试： `mvn test` 绿了吗？新增的逻辑有没有测试覆盖？
- 验收： 它做的是计划里要的那件事吗？有没有夹带私货？

三个都是"是"→ 合。有一个"否" → 判断是修还是弃。

我们这分支：测试绿、差异就一个 `ReportController` 和对应测试、做的事就是报表接口。 **结论：合。**

### 第三步：合——用不产生垃圾历史的合

回到主工作区，把分支合进来。为了历史干净，用 `--no-ff` （保留一个明确的"合并提交"，方便以后回溯这次合并）：

```
cd 202608-superpowers
git checkout main
git pull                       # 先拉最新，避免基于过期的 main 合并
git merge --no-ff report-backend -m "merge: 报表月度汇总接口"
```

合完， **立刻在主干上再跑一遍测试** ——这是合并后最容易被跳过、也最重要的一步：

```
"$MAVEN_HOME/bin/mvn" test
```

### 第四步：收尾清理

分支使命完成，删掉分支、拆掉工作区：

```
git branch -d report-backend
git worktree remove ../hl-be-report
```

`-d` （小写）只在分支已合并时允许删除—— **如果它提示"未完全合并"，说明你有东西忘了合，别用 `-D` 强删** 。

## 三种结局的判断清单

收尾不是无脑合。把这当checklist用：

| 检查项 | 过 | 不过怎么办 |
| --- | --- | --- |
| 代码审查通过 | 合 | 有疑点 → 修；看不懂 → 先问 |
| 测试全绿 | 合 | 修到绿为止 |
| 与验收对齐 | 合 | 方向对 → 修；方向错 → 弃 |
| 主线是最新 | 先拉再合 | — |
| 合完主干再测一遍 | 收工 | 红了立刻回退 |

特别说"弃"这一格： **弃分支不丢脸，死扛才是浪费。** 我们曾经有个"预算自动调额"的分支，写到一半发现跟艳姐的验收对不上，果断 `git branch -D` 弃掉，重开。省下的时间，够多写两个功能。

## 注意事项

1. 测试是合并的硬门槛。 分支测试不绿，不进主线。主线永远要绿，是团队的底线。
2. `git diff main...branch` 一定要看。 合之前不看差异，等于闭着眼验收。
3. `--no-ff` 让历史可追溯。 保留合并提交，以后查"这功能哪来的"一查一个准。
4. 合完在主干再测一遍。 分支上绿 ≠ 合完绿。合并冲突可能把好好的代码弄坏，主干测绿才算完。

## 本文小结

`finishing-a-development-branch` 把"合分支"从拍脑袋变成四步流程：自检 → 判断（合/修/弃）→ 安全合并 → 清理。 **测试绿、审查过、验收对，才有资格进主线。**
