老王在笔记里画了个圈：「你修完 bug 那个动作——‘跑一遍测试、验证修对了’——是不是有专门的说法？」

「有，」我答，「而且它是 superpowers 调试类里我最心疼的一条。因为 **我在这上面栽过最大的跟头** 。」

## 场景：改完就宣布完成，然后线上又炸了

那是幸福账本刚上线报表功能那会儿。

我发现报表接口有个小问题，改了两行代码。手快，改完直接 `git commit -m "fix: 报表修复"` ，跟艳姐说"修好了"。

第二天，艳姐冷着脸找我：「报表又不对了。」

我打开一看——我的"修复"修好了 A 场景，却把 B 场景弄坏了。 **因为改完那两行，我压根没跑测试，也没在页面验证。**

`verification-before-completion` （验证再收工）讲的不是"怎么修 bug"，而是： **宣布完成之前，你必须拿出证据证明它真的完成。** 这可能是 superpowers 里最"反人性"也最值钱的一条。

## 技能是什么：完成 ≠ 改完，完成 = 验证过

`verification-before-completion` 的核心是区分两个词：

- 改完了（implemented）： 代码动了，自认为对了；
- 完成了（completed）： **验证过了** ，有证据证明它对。

它要求在宣布"完成"前，过一套验证：

1. 代码层面的验证： 测试跑绿、编译通过、lint 无报错；
2. 行为层面的验证： 在真实运行环境里，把改动的功能 **实际走一遍** ；
3. 验收对照： 对着需求/计划的验收标准，逐条核对。

**证据可以是测试输出、截图、接口返回，但不能是"我觉得应该没问题"。**

## 怎么用：一次"修好又改坏"的教训，变成一套验证流程

那次教训之后，我给"修复"定了一套收工流程，拿一次真实修复演示。

### 场景：预算页"吃饭"分类超支没标红

艳姐报：预算页"吃饭"8 月已超支，却没标红。我排查发现，前端标红的条件是 `spent > limitAmount` ，而后端返回的 `spent` 是 `null` ——因为某分类没账时后端返回了 null，前端 `null > 2000` 是 false，自然不标红。

修复：前端把 `spent` 为空时按 0 处理。

### 第一步：改完，先跑代码层验证

改完 `Budgets.vue` ，第一件事不是提交，是跑测试。前端和后端都跑：

```
cd happy-ledger-web && npm test     # 前端 Vitest
cd happy-ledger && "$MAVEN_HOME/bin/mvn" test   # 后端 JUnit
```

（这版改动只动前端，后端测试是顺带确认没碰坏。）

### 第二步：行为层验证——真的在页面上走一遍

测试绿 ≠ 页面好。我起后端、起前端， **在浏览器里真的走一遍** ：

1. 打开预算页，选 8 月；
2. 找"吃饭"分类——已超支（支出 103.50 > 预算 2000？不对，吃饭没超）；
3. 那我得再造一个超支场景：把"吃饭"预算调成 50 元，再看它标不标红。

浏览器里：把"吃饭"预算改成 50，保存，刷新—— **"吃饭"红了，顶部弹出"吃饭 超支"提示。**

这就是行为层验证： **不是在脑子里过一遍，是在真实的页面上点一遍。**

### 第三步：验收对照——当初的问题，现在还在吗

回到艳姐报的那个具体现象：“吃饭超支没标红”。对照验收：

- 现象复现路径：吃饭预算 50 < 支出 103.5 → 应标红 → **现在红了** ✓
- 顺带检查没改坏的地方：没超支的分类不红 ✓、预算页其他操作正常 ✓

### 第四步：防回归 + 提交

把"空 spent 按 0"这条，加个前端测试钉死：

```
it('spent 为空时不误判为超支', () => {
  expect(isOverBudget(null, 2000)).toBe(false)
})
```

绿了，才提交：

```
git add src/views/Budgets.vue src/composables/overBudget.spec.js
git commit -m "fix: 预算超支标红 - spent 为空按 0 处理"
```

**这一次，我提交的时候是真的敢说"完成"——因为每一步都有证据。**

## 验证的"三问"清单

宣布完成前，问自己三句话：

1. 测试绿了吗？（ `mvn test`
	/ `npm test` 的输出贴出来）
2. 在真实环境走过了吗？（页面点过 / 接口 curl 过，不只是想想）
3. 对照验收标准逐条过了吗？（当初说好要达成的那几件事，全做到了？）

三个都是"是"，才算完成。任何一个"我猜应该没问题"——都回去补验证。

## 注意事项

1. "改完"和"完成"是两回事。 没有验证证据，你宣布的"完成"只是"改完"的客气说法。
2. 测试绿不等于行为对。 自动化测试覆盖不到的地方（渲染、交互、真实数据），要用手在页面上走一遍。前端改动尤其如此。
3. 验收对照要对着"现象"，不是对着"代码"。 艳姐报的是"吃饭没标红"，你要验证的就是"吃饭现在标红了"，而不是"我改了 xxx 行"。
4. 防回归测试别偷懒。 修完不加测试，等于告诉 bug：欢迎再来。

## 本文小结

`verification-before-completion` 把"完成"重新定义为"验证过"：测试绿 + 真实环境走一遍 + 验收对照。 **没有证据的完成，都是口头完成。**

这套收工流程跑顺之后，我提交代码的手，稳了很多。老王却盯着我那套"测试 + 手测 + 验收"的流程，问了句：

「你这些防线——入口校验、哨兵测试、验证再收工——都是一层一层的。要是 AI 写的代码绕过了第一层，第二层还能兜住吗？」

「这就是我接下来要讲的。」我笑了，「防线，本来就是用来一层一层叠的。」
