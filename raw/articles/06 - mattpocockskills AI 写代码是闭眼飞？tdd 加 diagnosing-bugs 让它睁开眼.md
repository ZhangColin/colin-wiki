## 前言

你让 AI 给 EShop 加个下单功能。它咔咔一顿写，代码给你整出来了。

你满怀期待跑一下。

红了。

报错。

你让它改。它改了，再跑，还是红。又改，又跑，又错。

改到第五轮，你终于明白了，这 AI 根本不知道自己写错了。。。它闭着眼，在飞。

我跟你讲，这个场景我太熟了。前五课我们解决了「AI 没做你要的事」，但还有一个更伤自尊的坑没处理，AI 做了你要的事，代码是坏的。

02 课说过原因，AI 写代码是「闭眼飞」的，没有反馈回路，它不知道自己写错了。这一课，把这条回路给它装上。

两把钥匙。

`tdd` ，写代码之前，先让 AI 看见「什么是对的」。

`diagnosing-bugs` ，代码坏了，让 AI 按科学方法修，而不是瞎猜。

一个管「不写坏」，一个管「修好」，合起来，就是 AI 编码的反馈回路。

我必须承认，这一课是整套技能里离我最近的。tdd、self-testing code、重构的安全网，这些是我写了二十多年的东西。所以这一课我不只是转述 Matt 的设计，我会用我自己的框架来检验它，包括它哪里对、哪里有过誉。

## tdd，红 → 绿 → 重构

`tdd` 的核心是红绿重构三循环。用 The Pragmatic Programmer 的话说，始终走小而谨慎的步子，反馈速度就是你的限速。翻译成 AI 能执行的流程。

```
红：先写一个会失败的测试，确认它因为正确的原因失败
绿：写最小实现，让测试通过
重构：在不改变行为的前提下整理代码，测试保持通过
```

先说历史。红绿重构这个节奏，源头是 Kent Beck 在 XP 里推广的 test-driven development。我写过，我自认的大部分工作，就是「把 Kent Beck 的想法写下来」。Matt 的贡献不是发明了 tdd，而是把它变成 AI 的强制流程。对 AI 来说，这个「强制」很关键，因为 AI 天生没有「先想清楚再动手」的耐心。

### 红，先写会失败的测试

假设 EShop 要写 `OrderService.createOrder()` 。AI 的第一件事不是写实现，是先写测试。

```
// OrderServiceTest.java
@Test
void createOrderWithFullReduction() {
    // 一个订单，总额 1200 元，满 1000 减 50
    CreateOrderRequest request = new CreateOrderRequest();
    request.setItems(List.of(
        new OrderItem(1001L, 600, 2)  // 单价 600，数量 2
    ));

    OrderVO result = orderService.createOrder(request);

    assertEquals(BigDecimal.valueOf(1150), result.getTotalPrice());
}
```

写完之后先跑一遍，它会失败。关键在这一步，AI 要确认这个失败是「因为实现没写」而失败，而不是测试本身写错了。失败原因对不对，决定了测试是不是真的在验证需求。

这一步的细节经常被忽略，但它是 tdd 里最值钱的一步。测试失败要「因正确的原因失败」。如果测试因为断言写错而失败，你修实现是修不好的。我见过太多人跳过这个确认，最后测试绿了，但测的东西根本不是需求。

### 绿，写最小实现

测试失败了，AI 才动手写实现。

```
public OrderVO createOrder(CreateOrderRequest request) {
    BigDecimal total = request.getItems().stream()
        .map(item -> item.getUnitPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
        .reduce(BigDecimal.ZERO, BigDecimal::add);
    // 满 1000 减 50
    if (total.compareTo(BigDecimal.valueOf(1000)) >= 0) {
        total = total.subtract(BigDecimal.valueOf(50));
    }
    // ... 预占库存、返回 VO
}
```

再跑测试，绿色。实现「刚好能通过」，不多写一行。

### 重构，整理，但不改变行为

测试绿了，AI 可以把那段内联的满减逻辑抽成方法，把魔法数 `1000` 、 `50` 换成常量，甚至查数据库读满减配置。重构完再跑一遍，还是绿。

这一步的意义，测试就是重构的安全网。没有它，AI 每次改动都是裸奔。有它，随便改，绿了就说明没改坏。

这里我要回到我的《Refactoring》。重构的定义是「在不改变外部行为的前提下改善内部结构」，它成立的唯一前提，是有一组可靠的测试兜底。没有测试的重构不是重构，是赌博。这套技能把「测试 → 重构」的绑定关系直接编码进了 AI 的流程，方向是对的。

### 关键纪律，一次只写一个测试

tdd 最大的纪律是「垂直切片」，一次只处理一个测试，红了变绿，绿了再写下一个。不要一口气写十个测试、十个实现。步子小，反馈快，出问题能精确定位到哪一步。

## diagnosing-bugs，复现 → 最小化 → 假设 → 修复 → 回归

tdd 管「不写坏」，但总有些 bug 是测试覆盖不到的，环境问题、并发问题、历史遗留。这时候 `diagnosing-bugs` 出场，它的循环是，

```
复现 → 最小化 → 假设 → 插桩验证 → 修复 → 回归
```

### 场景，EShop 退款金额算错

假设用户报了个 bug，满 1000 减 50 的订单，退款时只退了部分金额。AI 收到后， `diagnosing-bugs` 会这样走。

第 1 步，复现。先造一个能稳定复现的测试，确认 bug 存在。

```
@Test
void refundWithPaidAmount() {
    // 下单实付 1150，退款应退 1150，而不是 1200
}
```

第 2 步，最小化。把问题缩到最小。不是「整个退款流程有问题」，而是「满减订单的退款基数是 1200 而不是 1150」。缩到一行代码能说清。

第 3 步，假设。AI 提出假设，「退款用的是订单原始金额，没算满减后的实付金额」。

第 4 步，插桩验证。在 `AfterSaleOrderService.refund()` 里打印入参和计算过程，确认假设成立。

第 5 步，修复。改成用实付金额做退款基数。

第 6 步，回归。跑全量相关测试，确认修复没破坏别的场景。

写到这里我想起一件事。你去看病，医生不会瞄你一眼就开药，他会先检查，再判断，再开药。诊断这两个字，本来就是医学的词。AI 修 bug 也是这个理，先复现，先假设，先验证，最后才动手。跳过诊断直接改，跟跳过检查直接开药一样，是拿病人当实验品。

### 反模式，不插桩，直接改

没有 `diagnosing-bugs` 时，AI 最典型的坏习惯是「猜」。看到「退款金额不对」，直接改一行数字，跑了不报错就以为修好了？？？那根本不是修复，是碰运气。

`diagnosing-bugs` 逼它走完六步，尤其「插桩验证假设」这一步，让修复建立在证据上而不是猜测上。

我尤其欣赏「先复现、再假设、后修复」的顺序。这是我调试多年总结出的纪律，先让 bug 稳定出现，再解释它为什么出现，最后才动手改。跳过前两步直接改，是新手最常见的错误。这套技能把它做成了流程。

## 两套合起来，兜住什么

把两套合起来看，它们补的是 AI 编码的两个致命缺口。

tdd 补「事前」。AI 在写代码前就有了「对的基准」，那个会失败的测试，它不再闭眼飞。

diagnosing-bugs 补「事后」。代码坏了，AI 有科学的排错流程，不再瞎猜。

看明白了吗，这两件事，其实是同一件事的两面。都遵循同一个底层逻辑，反馈速度就是限速。测试告诉你对不对，秒级反馈。插桩告诉你错在哪，证据反馈。反馈越快，AI 的步子才能越稳。

## 两个反指标，别掉坑

这套技能好归好，但有两个地方特别容易用歪，我单独拿出来说。

第一，别把覆盖率当目标。覆盖率是衡量测试好坏的最直观指标，所以它最容易变成考核指标。但覆盖率再高，也测不出「你测错了断言」的问题。我见过 100% 覆盖率、照样一堆 bug 的项目，也见过 60% 覆盖率、稳如泰山的项目。真正该盯的是「测试有没有测到该测的行为」，不是百分比。给 AI 设「覆盖率必须 95%」的门禁，是把手段当目标。

第二，测试不是银弹。self-testing code 抓不住所有回归，性能退化、远端副作用、并发时序，测试往往无能为力。tdd 能兜住大部分「逻辑错误」，但兜不住「环境错误」。这不是缺陷，是测试的本性。明白这一点，你就不会在测试全绿时掉以轻心。

这两个提醒，说到底是我那句 CannotMeasureProductivity 的延伸，容易量化的指标，往往不是真正重要的指标，真正重要的东西，常常没法用数字证明。

## 何时不要用

照例，补一节边界。

一次性脚本、探索原型，别上 tdd。扔了就扔的代码，测试的投入收不回。先跑起来看效果，比先写测试更合理。

纯配置改动，别上 tdd。改个数据库连接串、调个部署参数，没有可测的业务逻辑，测试无从写起。

团队没测试文化时，先别强推 tdd。tdd 是个习惯，需要时间养成。如果团队连「跑一遍测试」都嫌麻烦，直接上红绿重构只会适得其反。我见过太多团队把 tdd 当成必须执行的仪式，结果测试全是最小化的假绿。从「先写几个关键测试」开始，比一步到位强。

回到开头那个场景。AI 咔咔一顿写，你满怀期待跑一下。

红了。

报错。

以后不会了。

先写测试，让 AI 在动手之前，先看见什么是对的。写错了，走六步排错，让修复建立在证据上。

它睁开眼了。

代码真的能跑了。
