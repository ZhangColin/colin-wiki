做 AgentScope Java 的第一个 Web 上手，我不建议一上来就接 Shell、文件系统、Workspace 和一堆工具。

先把入口搭稳。

后端项目里，真正麻烦的不是让模型回一句话，而是把 Agent 放到 HTTP 接口后面：请求怎么进来，流式结果怎么出去，会话怎么区分，哪些能力暂时不能给模型用。

如果一开始只写成：

text

Controller -> Model -> String

后面接工具、权限确认、状态恢复和事件流时，很快就会重写。

这里先搭一条更接近真实后端项目的链路：

text

HTTP 请求

\-> Controller

\-> Service

\-> HarnessAgent

\-> RuntimeContext(userId, sessionId)

\-> DeepSeek

\-> SSE 流式返回

这个接口接收一个研发任务，把模型整理出来的执行清单通过 SSE 返回。它不向模型暴露工具，也不给文件读写权限；状态先放在当前进程里。

目标很清楚：

text

先把 Web 入口、流式输出、会话边界跑通

再往里面加工具、权限和持久化

## 一、先把项目跑起来

这套代码用的是：

text

JDK 17

Maven 3.9+

Spring Boot 4.1.0

AgentScope Java 2.0.0

deepseek-v4-flash

AgentScope Java 2.0 的构建基线是 JDK 17，Quickstart 推荐 Maven 3.9 及以上版本。

官方依赖 BOM 里管理的 Spring Boot 版本是 4.0.4。这里用 Spring Boot 4.1.0，它能编译运行，但这不等于 AgentScope Java 声明“最高只支持”或“完整认证”某个 Spring Boot 版本。换版本时，还是要以项目依赖验证为准。

`pom.xml` 需要 Harness、OpenAI-compatible 模型实现和 Spring Web：

xml

\<properties>

<java.version>17</java.version>

<agentscope.version>2.0.0</agentscope.version>

\</properties>

\<dependencies>

\<dependency>

\<groupId>io.agentscope\</groupId>

\<artifactId>agentscope-harness\</artifactId>

\<version>${agentscope.version}\</version>

\</dependency>

\<dependency>

\<groupId>io.agentscope\</groupId>

\<artifactId>agentscope-extensions-model-openai\</artifactId>

\<version>${agentscope.version}\</version>

\</dependency>

\<dependency>

\<groupId>org.springframework.boot\</groupId>

\<artifactId>spring-boot-starter-web\</artifactId>

\</dependency>

\<dependency>

\<groupId>org.springframework.boot\</groupId>

\<artifactId>spring-boot-starter-validation\</artifactId>

\</dependency>

\</dependencies>

`agentscope-harness` 会带上核心运行时包。 `agentscope-extensions-model-openai` 提供 `OpenAIChatModel` 和 `DeepSeekFormatter` ，这里用它接 DeepSeek 的 OpenAI-compatible 接口。

## 二、配置先收住边界

`application.yml` ：

yaml

server:

port: 8080

app:

dev-agent:

name: dev-task-agent

system-prompt: |

你是一个研发任务整理助手。

用户给出一个待处理的问题后，把它整理成简洁、可执行的检查清单。

当前没有接入项目文件、日志、数据库或外部工具，不要声称已经完成查询、修改或保存。

信息不足时指出需要补充的关键内容，不要编造排查结果。

回答控制在 6 条以内，每条只写一个检查动作，不写开场白和总结。

使用中文回答。

model:

api-key: ${DEEPSEEK\_API\_KEY}

base-url: https://api.deepseek.com

name: deepseek-v4-flash

这个 Agent 暂时没有日志查询、项目读取和数据库访问能力，只能根据用户输入整理检查顺序。

Prompt 里要把边界写清楚：不能假装已经查过日志，也不能说自己修好了问题。这个限制不是装饰，接工具以后也一样重要。模型不知道自己有没有能力，应用要告诉它。

配置用 `@ConfigurationProperties` ：

java

@Validated

@ConfigurationProperties(prefix = "app.dev-agent")

public record DevAgentProperties(

@NotBlank String name,

@NotBlank String systemPrompt,

@Valid Model model) {

public record Model(

@NotBlank String apiKey,

@NotBlank String baseUrl,

@NotBlank String name) {

}

}

启动类启用配置绑定：

java

@SpringBootApplication

@EnableConfigurationProperties(DevAgentProperties.class)

public class AgentScopeJavaApplication {

public static void main(String\[\] args) {

SpringApplication.run(AgentScopeJavaApplication.class, args);

}

}

## 三、创建一个克制的 HarnessAgent

先把 DeepSeek 模型包装成 AgentScope 的 `Model` ：

java

@Bean

Model deepSeekModel(DevAgentProperties properties) {

DevAgentProperties.Model model = properties.model();

return OpenAIChatModel.builder()

.apiKey(model.apiKey())

.baseUrl(model.baseUrl())

.modelName(model.name())

.formatter(new DeepSeekFormatter())

.stream(true)

.build();

}

`.stream(true)` 打开流式输出，后面的 Web 接口才能边生成边返回。

再创建 `HarnessAgent` ：

java

@Bean

HarnessAgent devAgent(

Model deepSeekModel,

DevAgentProperties properties) throws IOException {

HarnessAgent agent = HarnessAgent.builder()

.name(properties.name())

.sysPrompt(properties.systemPrompt())

.model(deepSeekModel)

.stateStore(new InMemoryAgentStateStore())

.enableAgentTracingLog(false)

.disableFilesystemTools()

.disableShellTool()

.disableMemoryTools()

.disableMemoryHooks()

.disableCompaction()

.disableSubagents()

.disableWorkspaceContext()

.disableAtPathExpansion()

.disableDynamicSkills()

.disableDefaultWorkspaceSkills()

.disableToolsConfig()

.build();

agent.getToolkit().removeTool("wait\_async\_results");

return agent;

}

这段 builder 看起来有点长，原因很简单： `HarnessAgent` 面向的是一个更完整的 Agent 运行时，会涉及 Workspace、记忆、子 Agent、工具、动态 Skill 等能力。

但这个接口只做第一件事：让 Agent 通过 Web 接口完成一次流式回答。

这里主动关掉文件系统、Shell、记忆、子 Agent、Workspace 上下文和动态 Skill。 `disableFilesystemTools()` 、 `disableMemoryTools()` 、 `disableSubagents()` 这类方法主要影响工具注册； `disableMemoryHooks()` 、 `disableCompaction()` 、 `disableWorkspaceContext()` 则会影响记忆维护、上下文压缩和工作区上下文注入。

即使关闭子 Agent，Harness 默认消息总线仍会注册 `wait_async_results` 。这次用不到，所以最后移除。启动后，这个 Agent 的 Toolkit 里没有可供模型调用的工具。

`InMemoryAgentStateStore` 只在当前进程里保存状态，应用一旦重启，数据就没了。需要跨进程恢复时，可以换成内置的 `JsonFileAgentStateStore` 、Redis 扩展，或者自己实现 `AgentStateStore` 。

## 四、把用户和会话带进去

HTTP 请求只保留三个字段：

java

public record DevAgentRequest(

String userId,

@NotBlank String sessionId,

@NotBlank String message) {

}

`message` 是这次输入， `sessionId` 是会话编号， `userId` 是用户身份。

这里没有给 `userId` 加 `@NotBlank` ，是为了本地测试可以不传。真实系统里不要直接相信前端传来的 `userId` ，更稳的做法是从登录态、网关 Token 或服务端 Session 里取。

流式响应统一成三种业务消息：

java

public record DevAgentEvent(

String type,

String sessionId,

String content) {

public static DevAgentEvent session(String sessionId) {

return new DevAgentEvent("SESSION", sessionId, "");

}

public static DevAgentEvent message(

String sessionId,

String content) {

return new DevAgentEvent("MESSAGE", sessionId, content);

}

public static DevAgentEvent done(String sessionId) {

return new DevAgentEvent("DONE", sessionId, "");

}

}

Service 里把 `sessionId` 和可选的 `userId` 放进 `RuntimeContext` ，再从事件流里取出文本增量：

java

public Flux\<DevAgentEvent> ask(DevAgentRequest request) {

RuntimeContext.Builder contextBuilder = RuntimeContext.builder()

.sessionId(request.sessionId());

if (request.userId()!= null &&!request.userId().isBlank()) {

contextBuilder.userId(request.userId().strip());

}

RuntimeContext context = contextBuilder.build();

Flux\<DevAgentEvent> messages = devAgent

.streamEvents(request.message(), context)

.ofType(TextBlockDeltaEvent.class)

.map(event -> DevAgentEvent.message(

request.sessionId(),

event.getDelta()));

return Flux.concat(

Mono.just(DevAgentEvent.session(request.sessionId())),

messages,

Mono.just(DevAgentEvent.done(request.sessionId())));

}

`RuntimeContext` 是这段代码的关键。

普通模型接口更多是在处理这次 Prompt。 `HarnessAgent` 会根据 `RuntimeContext` 里的 `(userId, sessionId)` 找到对应的 Agent 状态。同一个 `HarnessAgent` Bean 可以服务多个用户、多段会话，不需要每个用户 new 一个 Agent。

`streamEvents()` 返回 `Flux<AgentEvent>` 。一次执行除了文本，还可能产生工具调用、工具结果和确认请求等事件。这个接口没有工具，只取 `TextBlockDeltaEvent` ，把模型生成的文字逐段送给前端。

Controller 保持很薄：

java

@RestController

@RequestMapping("/dev-agent")

public class DevAgentController {

private final DevAgentService devAgentService;

public DevAgentController(DevAgentService devAgentService) {

this.devAgentService = devAgentService;

}

@PostMapping(path = "/ask",

produces = MediaType.TEXT\_EVENT\_STREAM\_VALUE)

public Flux\<DevAgentEvent> ask(

@Valid @RequestBody DevAgentRequest request) {

return devAgentService.ask(request);

}

}

项目仍然使用 Spring MVC。 `Flux` 在这里作为流式返回值，由 Spring Web 按 SSE 写回客户端，不需要为了一个接口把整个项目切成 WebFlux 应用。

但这不等于全链路非阻塞。Spring MVC 写响应时仍然是 Servlet 模型，生产环境还要配置合适的异步执行器、超时时间和 SSE 心跳。

## 五、用 curl 看流式返回

启动前配置 API Key：

bash

export DEEPSEEK\_API\_KEY=<你的 API Key>

mvn spring-boot:run

再打开一个终端：

bash

curl -N -X POST "http://localhost:8080/dev-agent/ask" \\

\-H "Content-Type: application/json" \\

\-d '{

"userId":"dev-user-001",

"sessionId":"dev-session-001",

"message":"帮我整理一份今天排查订单接口超时的执行清单"

}'

`-N` 会关闭 curl 的输出缓冲。终端会先拿到 `SESSION` ，随后持续收到模型文本；请求正常完成时，最后收到 `DONE` 。

模型每次吐出的片段不固定，可能是一个词，也可能只有一两个字。示例里把部分连续片段合并展示：

text

data:{"type":"SESSION","sessionId":"dev-session-001","content":""}

data:{"type":"MESSAGE","sessionId":"dev-session-001","content":"1."}

data:{"type":"MESSAGE","sessionId":"dev-session-001","content":"确认订单接口出现超时的时间段"}

...

data:{"type":"DONE","sessionId":"dev-session-001","content":""}

模型回答的具体措辞不固定，但方向应该是一份排查清单，而且不能声称已经读取日志、执行命令或定位出具体故障。

再用同一个 `userId` 和 `sessionId` 问一句：

bash

curl -N -X POST "http://localhost:8080/dev-agent/ask" \\

\-H "Content-Type: application/json" \\

\-d '{

"userId":"dev-user-001",

"sessionId":"dev-session-001",

"message":"我刚才让你整理的是什么任务？一句话回答"

}'

状态正常时，模型会知道上一轮是在整理“订单接口超时”的排查清单。

再换一个 `sessionId` ：

bash

curl -N -X POST "http://localhost:8080/dev-agent/ask" \\

\-H "Content-Type: application/json" \\

\-d '{

"userId":"dev-user-001",

"sessionId":"dev-session-002",

"message":"我刚才让你整理的是什么任务？不知道就说不知道"

}'

这次它不应该拿到上一段会话里的内容。

这两个测试比只看第一段输出更关键。它能说明 `RuntimeContext` 和 `AgentStateStore` 已经参与执行，而不只是把模型返回包装成 SSE。

## 写在最后

到这里， `HarnessAgent` 已经接进 Spring Boot，并通过 Controller、参数校验、 `RuntimeContext` 和 SSE 对外提供服务。

代码不多，边界很清楚：它会整理执行清单，但不会查日志、读项目、改文件。

很多 Agent Demo 容易一上来就把工具全打开：文件系统、Shell、记忆、Workspace、子 Agent，全接上。看起来很完整，但一旦回答不符合预期，很难判断到底是模型没听懂、Prompt 没写清楚、工具返回脏数据，还是状态串了。

这一版故意只保留最小闭环：HTTP 入口、参数校验、会话信息、流式返回。先跑通这四件事，再加工具，问题边界会清楚很多。

后面如果要接日志查询工具，就只看工具调用和工具结果；如果要换持久化状态，就只看 `AgentStateStore` ；如果要做权限确认，就只看事件流里怎么把确认请求透给前端。

入口先别做太满，不是为了写一个弱 Agent，而是为了让每一层能力都有地方落，也都有办法测试。
