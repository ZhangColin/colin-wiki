## 前言

你有没有发现，AI 越用越不对劲。

头三个月，它像刚入职的天才，你说加个功能，一句话它就写对了。三个月后，同样一句话，它开始反复跟你确认，写出来的东西还经常跑偏。你怀疑是不是模型变笨了，换更强的模型，问题照旧。

AI 没变，你的代码库变了。

它每次动手前，都要读一遍你的代码库。读你的模块怎么搭、术语怎么叫、约定是什么。代码库越乱，它读得越慢，猜得越偏，写完之后又留下更多乱。这是个循环，循环的起点，是你从没认真看过自己的代码库。

浆糊是攒出来的，攒的过程里你多半没看见。新功能越加越多，模块边界被撑变形，改一处要牵连三处。这些你都有感觉，只是没人说出来。团队里承认代码烂，等于承认自己没管好，于是人人都说「这代码好乱」，然后继续加功能。

`improve-codebase-architecture` 干的事，就是把这层看不见的浆糊，摆到台面上。

它扫一遍代码库，把值得动的地方找出来，你挑一个，它陪你聊到底。它只读，不写。干活分三步，扫出热点、摆出候选、挑一个聊到底，我们一路跟下来。

## 阶段一，Explore，先定范围再扫描

体检不是把整个代码库翻一遍。技能自己的第一句纪律，动手扫之前，先决定往哪儿看。YAGNI，范围优先。

如果用户直接点名了方向，一个模块、一个子系统，或者只说得出哪块让你难受，那就取这个方向，跳过后面的推断。多数时候没有，那就走推断。

往回翻一段 git 历史， `git log --oneline` ，找出代码库的热点，那些反复出现的文件和区域。热点决定了往哪儿看。如果改动散布得没有热点，再扩大范围。

这一步背后的道理很实在。深折一个模块，靠的是它未来的改动更容易，所以最近频繁变动的部分，权重最高。一个半年没碰过的模块，再乱也不急着动它。

拿 EShop 举例。订单创建这块区域最近改动最勤，优惠券、满减、会员价一次次往这里堆，git 历史翻出来一片全是它。热点就是这儿，扫描的重点就落在订单创建上。

范围定了，先读项目的领域词汇表（CONTEXT.md）和这片区域相关的 ADR。词汇表给你好接缝的名字，ADR 记录了过去已经拍板、这次不该重新吵的决定。

然后派 Explore 子代理走查代码库，不用死板的清单，顺着走，记下你感到摩擦的地方。

- 理解一个概念，是不是要在许多小模块之间来回跳？
- 哪些模块是浅的，接口几乎和实现一样复杂？
- 是不是为了可测性把纯函数抽出来，但真正的 bug 藏在调用方式里，没有局部性？
- 紧耦合的模块是不是跨过了自己的接缝泄漏？
- 哪些部分没测试，或者当前接口很难测？

走到这儿要认两个词，它们是你接下来看懂报告的关键。一个模块是深的，当大量行为藏在一个小接口后面。它是浅的，当接口几乎和实现一样复杂。拿图说话。

```
浅模块                     深模块
┌─────────────────────┐   ┌─────────────────────┐
│   Large Interface   │   │  Small Interface    │
├─────────────────────┤   ├─────────────────────┤
│  Thin Implementation│   │                     │
│  Just passes through│   │ Deep Implementation │
└─────────────────────┘   └─────────────────────┘
```

对任何疑似浅的模块，跑一遍删除测试。想象把这个模块删掉，复杂度会消失，它就是个透传的壳。复杂度会重新散布到 N 个调用方手里，它值得留着。删掉它，复杂度是消失，还是只是搬家？答案是搬家，这就是你要的信号。

## 阶段二，HTML 报告，把病灶摆到台面上

扫描完，产出是一份自包含的 HTML 报告，写到系统临时目录，不落进仓库，然后自动在浏览器打开。样式走 Tailwind，图表用 Mermaid 加手绘 SVG，一个候选一张卡片，每个都配 before/after 对比图。

卡片上的字段固定五个。Files 列涉及的文件；Problem 一句话说清现在哪里难受；Solution 一句话说清会怎么变；Benefits 用 leverage 和 locality 的说法讲收益，顺带说明测试会怎么变好；Recommendation strength 标推荐强度，Strong / Worth exploring / Speculative 三档，用徽章标出来。

两个词先认一下。leverage，杠杆，调用方从深度得到的东西，一份实现回馈 N 个调用点和 M 个测试。locality，局部性，维护者从深度得到的东西，变更、bug、知识、验证集中在一处，改一次，处处生效。报告里说「收益」的时候，多半就是在说这两样。

最后是一节 Top recommendation，先动哪个，为什么。

报告里有个词汇纪律，比画图更重要。领域概念用 CONTEXT.md 的说法，架构概念用 codebase-design 的说法。如果 CONTEXT.md 里定义了 Order，就说「Order 接收模块」，不叫它 FooBarHandler，也不叫它 Order service。术语一乱，报告就失去了一半价值。

来，看一份真实的体检报告。拿 EShop 举例，一个 Java Spring Boot 电商项目，功能越加越多，优惠券、满减、会员价都堆了进来，订单创建的模块边界已经被撑变形了。扫描报告给出三个候选，主推第一个。

**候选一，折叠订单创建管线** ，Strong。

```
Files: OrderController / OrderService / OrderValidator / OrderPriceCalculator / OrderRepo
Problem: 订单创建被拆成一串浅模块，每个都很薄，真正的逻辑散落在调用处
Solution: 把校验和算价折进一个深模块，一个入口，内部保留接缝
Benefits: 测试只打一个接口；算价逻辑不再泄漏；删掉 4 个透传壳
```

before 和 after 用图说话。

订单管线体检前，一串浅模块，OrderPriceCalculator 还漏了一条线给调用方。

```
OrderController
└──→ OrderService
      ├──→ OrderValidator
      │     └──→ OrderRepo
      └──→ OrderPriceCalculator
            ├──→ OrderRepo
            └──→ PricingClient   ← pricing 泄漏到调用方
```

订单管线体检后，OrderIntake 一个深模块吃掉整条管线，Validator 和 PriceCalculator 退成内部接缝，外面只剩一个入口，到仓库的调用也收进去了。

```
OrderController
└──→ OrderIntake（深模块，唯一入口 createOrder）
      ├──→ Validator          ← 内部接缝
      ├──→ PriceCalculator    ← 内部接缝
      └──→ OrderRepo
```

这就是 leverage，一个接口，N 个调用点都用它，测试也只打它。浅模块的壳删掉之后，复杂度没有消失，只是集中进了这个深模块，这正是删除测试说该折的信号。

候选二「价格逻辑收回模块」和候选三「校验散落合并」也是这次扫描的真实发现，但都只是候选一的一部分，拆开做反而重复，排在 Worth exploring 和 Speculative 两档。

报告的 Top recommendation 是候选一。理由很直接，订单创建是 EShop 最近改动最频繁的区域，把整条浅管线折成一个深模块，一次收掉算价泄漏和透传壳两个问题，杠杆最大。

三个候选摆出来，技能在这里停下来。它不替你选，不替你重构，只问一句，你想看哪一个？

## 阶段三，grilling 循环，挑一个聊到底

你点了候选一。真正的重头戏从这儿开始。

技能回到 grilling 的路数，一次一个问题，每个问题附推荐答案，沿着决策树把这条分支走到头。跟聊需求不同，这次的问题对象从「要什么功能」换成了「这个深模块怎么切」。

第一问，OrderIntake 的接口长什么样？

推荐答案，一个入口方法，接收订单创建请求，返回订单结果。校验和算价都不暴露，调用方不知道里面有几道工序。接口越窄，深度越深。

```
OrderVO createOrder(CreateOrderRequest request);
```

这里顺便认一个词，seam，接缝。一个不用改动现场就能改变行为的地方，模块接口所在的位置。OrderIntake 外面那条接口线，就是一个接缝，调用方和测试都从这儿进出。

第二问，Validator 和 PriceCalculator 留在接口后面，还是完全并掉？

推荐答案，留在内部，作为内部接缝。深模块可以由一堆小的、可 mock、可替换的内部件组成，它们只是不属于接口。内部单测直接打它们，接口测试打 OrderIntake，两层各测各的。这正好用上「接口就是测试面」那条准则，调用方和测试走同一个接缝，你想测到接口后面去，多半是这个模块形状不对。

第三问，删除测试怎么验这个方案？

推荐答案，想想现在删掉 OrderService 这层壳，复杂度会怎样。它现在只负责把校验、算价、存库挨个喊一遍，删掉它复杂度直接消失，纯透传，该折。这个判断可以写进最后的 ADR。

第四问，pricing 泄漏怎么收？

推荐答案，PricingClient 从 Controller 挪进 PriceCalculator 内部。判断标准还是那条，一个适配器是假设接缝，两个才是真接缝。adapter，适配器，在接缝处满足接口的具体东西。EShop 生产环境用真实客户端，测试环境用内存假实现，两个适配器，这个接缝成立。如果只有生产一种，先别抽。

第五问，测试会怎么变？

推荐答案，原来打 OrderService 的测试改成打 OrderIntake，测试数不变，但每个测试都经过同一个接缝。算价和校验的单测留在内部接缝上。接口就是测试面，这句在这儿兑现。

五问下来，方案从折一下变成了接口长这样、内部怎么分、测试怎么摆都确定的施工图。

访谈过程里，domain-modeling 在旁边一直干活。OrderIntake 这个新概念，CONTEXT.md 里没有，聊到它定名的时候，当场写进词汇表。这是体检最常顺手产出的东西。

```
OrderIntake：订单域的深模块，订单创建的唯一入口，
校验与算价退为内部接缝，不向调用方暴露。
```

访谈里还有一个被否掉的候选值得一提。候选二「价格逻辑收回模块」，你看了候选一之后决定不做，理由是反正要跟着管线一起折，单独拆一遍是重复劳动。这个理由要留给未来的人，不然下次体检它还会再冒出来。技能会问一句，要不要记成 ADR？

记。这样以后任何人跑体检，看到这条 ADR，就知道这个决定已经被权衡过，不用再吵一遍。不是每个否决都值得记，只有这种「以后肯定还会再被建议」的承重理由才值得。

## 边界和误区

照例把坑一次说清。

**它只体检，不改代码** 。报告写进临时目录，不落仓库，不自动改任何东西。你选了一个候选，接下来生成一个想法，带进 `/grill-with-docs` 走正式流程。想让它顺手把代码改了，找错技能了。

**别先认定答案再扫描** 。你要是一进门就想着「价格模块该拆」，那扫描只是走个过场。它是侦查，不是证词。扫到什么算什么，让候选自己浮出来。

**别把它当万金油** 。它输出的候选质量，取决于你范围判断准不准。热点找偏了，报告再漂亮也是空中楼阁。范围先行那句纪律，是整套东西的地基。别给一次性交付的项目做体检，写完就不改的脚本、一次性的工具，深折没有回报。

最后交代一句它跟谁分工，免得你用它的时候串了台。它嘴里的词汇全从 codebase-design 来，一个给语言，一个用语言扫描。它挑中一个候选后生成一个想法，带进 `/grill-with-docs` 走正式流程，它只负责找到路，不负责走完路。 `diagnosing-bugs` 排错排到最后，如果发现病根是「没有好的测试接缝」「调用方缠成一团」，会把手上没修完的活递给它。三个角色记清楚，前后就接得上了。

## 回头看看那个循环

回到开头。AI 为什么越用越不对劲？

因为它每次写代码前，都要读一遍你的代码库。代码库缠成一团，AI 读不懂，写什么都是蒙的，写完之后又留下一团。循环每天都在转，只是你没看见。

浆糊是一点点攒出来的，攒的过程里你多半没看见。这套词汇加三阶段流程，就是那双能看见浆糊长什么样的眼睛。深折一个模块之前，你其实从没认真看过自己的代码库。

代码写久了会变浆糊。浆糊不是要推倒重来的理由，它只是一个信号，该体检了。让 AI 把病灶摆到台面上，挑一个，聊到底。

磨平一点信息差，哪怕只是你自己和昨天的自己之间，那一点。

## 快速回顾

- 核心机制，AI 靠读代码库写代码，代码库越浆糊 AI 越蠢，循环
- 定位，user-invoked 技能，只读既有代码，只体检不改代码
- 三阶段，Explore 先定范围（git log 找热点）→ HTML 报告摆候选 → grilling 聊到底
- 关键概念，深/浅模块、删除测试、接口就是测试面、一个适配器是假设接缝两个才是真接缝
- 报告，五字段卡片加 before/after 图加推荐强度，Top recommendation 收尾，不落仓库
- grilling 产物，接口定形、新词进
	CONTEXT.md、承重的否决记 ADR
- 分工，codebase-design 给词汇，grill-with-docs 接下游，diagnosing-bugs 递上游
- 别当万金油，热点找偏报告就是空中楼阁；一次性项目不值得体检

到这儿，这篇专题就写完了。下次你看着 AI 越用越不对劲，别急着换模型，先让它给你的代码库做一次体检。
