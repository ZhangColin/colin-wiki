## 智能问数平台设计：五层架构与十步落地

智能问数（NL2SQL）这两年很热，但很多团队的实现还停留在"能转 SQL"的阶段。转出来能不能跑、跑了对不对、用户敢不敢信——这些问题没人系统性地回答过。

这篇文章梳理一套从架构到实施的设计思路。

---

## 一、先把问题想明白

### 1.1 别再把智能问数理解成转 SQL

很多团队脑子里就一个等式：

```
用户说「查上月销售额」 → 系统转 SQL → 返回结果
```

这没毛病，但太粗了。智能问数要解决的问题其实就三句话：

**让不懂 SQL 的业务人员，能安全、准确地查到自己要的数据。**

三个关键词，每一个都踩在生产环境的痛点上：

- **不懂 SQL** — 目标用户是运营、销售、产品经理
- **准确** — 比查不出来更糟糕的是查出一堆错数据
- **安全** — 销售不能看人事数据，客服不能导全部客户信息

### 1.2 不同场景，难度完全不是一个量级

智能问数不是所有场景一视同仁的，按复杂度分四档：

| 级别 | 场景 | 例子 | 难度 |
| --- | --- | --- | --- |
| L1 | 单表查询 | orders 表有多少条记录？completed 的有多少？ | ⭐ |
| L2 | 多表关联 | 华东地区上个月复购率最高的品类是什么？ | ⭐⭐⭐ |
| L3 | 复杂指标 | GMV = 成交金额 + 运费 - 退款金额，查各渠道 GMV | ⭐⭐⭐⭐ |
| L4 | 自由探索 | 帮我看看上季度数据有什么问题，给结论 | ⭐⭐⭐⭐⭐ |

L1 做到 99% 准确率，L2 做到 85%，L3 靠预定义指标兜底，L4 现阶段只当辅助工具。不要一上来就全场景覆盖。

## 三、数据层：先把 Schema 理顺

### 3.1 数据层决定准确率

NL2SQL 的准确率，70% 靠数据层，30% 靠模型层。这话可能有人不信，但生产环境就是这样：

字段有注释、命名规范的数据库，NL2SQL 准确率轻松 95%+。字段叫 `c1` 、 `c2` 、 `f1` 、连表结构文档都没有的数据库，你用 GPT-4o 也救不回来，准确率可能不到 50%。

第一条原则： **先治理，再智能。**

### 3.2 语义层：在物理表和用户之间加一道翻译

物理表里的字段叫 `order_amt` 、 `user_id` 、 `created_at` ，但业务人员关心的是「销售额」「用户数」「下单时间」。语义层做翻译。

```
物理表：orders
    │
    ├── order_id
    ├── user_id
    ├── amount
    ├── status
    └── created_at
    │
    ▼ 语义映射
    │
    ├── 「销售额」→ SUM(amount) WHERE status IN ('已完成','已支付')
    ├── 「订单数」→ COUNT(order_id)
    ├── 「客单价」→ AVG(amount)
    └── 「复购」→ 购买2次及以上的用户占比
```

三个价值：

1. 屏蔽物理结构 — 用户看到的不是字段名，是业务术语
2. 统一口径 — 避免「销售额」和「GMV」到底是不是一个东西的争吵
3. 封装复杂逻辑 — 多表关联、过滤条件预先定义好

### 3.3 语义层怎么搭

两种方案：

**A. 基于 dbt** — 生态成熟，数据团队上手快。但得有现成的 dbt 基础设施，否则硬上反而增加复杂度。

**B. 自建轻量注册表** — 设计一套 Schema 注册协议，每张表注册表名、字段、注释、业务含义、关联关系，提供一个管理后台给数据团队维护。

轻量、可控、不绑定工具链，选 B 更实际。

## 四、NL2SQL 引擎：核心链路怎么走

```
用户问题 → 意图识别 → Schema 链接 → SQL 生成 → 校验 → 执行 → 结果
```

### 4.1 意图识别：不是所有问题都要转 SQL

「查上月销售额」— 走 NL2SQL 「帮我写个周报」— 走 LLM 文本生成 「把结果发我邮箱」— 走操作执行 「订单表结构啥样」— 走 Schema 查询

用一个小模型做分类就行。大模型只干 SQL 生成的活，省钱也省事。

### 4.2 Schema Linking：三步法

先提取关键词再做语义匹配，这个做法确实好用。

**第一步：粗筛**

用户说「上月华东销售额前五的产品」，系统从语义层快速匹配：

```
关键词：销售额、产品、华东、上月、前五
  → 销售额 → SUM(amount)  
  → 产品  → products.product_name
  → 华东  → orders.region = '华东'
  → 上月  → created_at 时间范围
  → 前五  → LIMIT 5
```

**第二步：上下文压缩**

从语义层拿到的结果，压缩成精简的 Schema 上下文，只包含当前查询需要的表和字段。把所有表结构一股脑塞给模型不是帮忙，是添乱。

**第三步：Prompt 构建**

把压缩后的 Schema 和原始问题拼成一个 Prompt 喂给模型。信息够用就行，多一个字都是浪费。

好处很明显：Token 消耗低，噪声少，模型不容易跑偏。

### 4.3 SQL 生成：分层模型，便宜又好用

不用一个大模型打天下，按复杂度分三路：

| 问题类型 | 模型 | 成功率 |
| --- | --- | --- |
| 简单（单表、聚合） | 小尺寸 | \>95% |
| 中等（多表关联） | 中等尺寸 | \>85% |
| 复杂（多关联+子查询） | 中大尺寸 | \>75% |

路由逻辑：意图识别阶段给问题打复杂度分，分低用小模型，分高中到大模型。小模型生成的 SQL 执行报错且 Self-Correction 搞不定时，再降级到大模型兜底。

### 4.4 SQL 校验：三道防火墙

生成的 SQL 不能直接跑，得先过三道关。

**第一道：语法检查** — 用 SQLParser 做静态分析，语法错误直接拦截。

**第二道：安全策略**

```
最大返回行数：10000
允许查询的表：白名单
禁止的操作：DROP / DELETE / TRUNCATE / ALTER
运行模式：只读
执行超时：30秒
```

这些规则硬编码在引擎里。

**第三道：执行环境隔离** — 所有 SQL 在只读副本上执行。

报错后 Self-Correction 上场：把错误信息 + 原始 Prompt 喂回给模型让它自己改，最多重试三次，还不行就友好提示用户。

## 五、服务层：体验好不好，全看这里

### 5.1 多轮对话

```
用户：查一下上个月华东的销售额
模型：365 万

用户：那华南呢？
模型：华南 218 万，华东环比增长 12.3%

用户：按城市拆开看看
模型：杭州 120万，上海 98万，南京 45万，苏州 37万…
```

关键是维护一个对话状态机，记录当前查了什么表、定了什么指标、过滤条件是什么。用户说「那华南呢」的时候，系统得知道「那」指的是销售额。

### 5.2 结果缓存

同样的查询没必要每次都重新生成 SQL、重新跑一遍。

缓存 key 用语义层解析后的标准化查询，不是简单 hash 问题文本。这样「上月」和「上一个自然月」只要解析结果一样就能命中。TTL 设 30 分钟，简单查询缓存命中率能到 60% 以上。

### 5.3 权限控制

权限不是最后加的一道锁，贯穿全链路：

```
用户发起查询
    ↓
解析 RBAC 权限（能查哪些库、表、字段）
    ↓
在 SQL 中自动注入 WHERE 条件（行级权限）
    ↓
Schema 上下文只暴露有权范围
    ↓
执行只读副本
    ↓
结果限 1000 行 + 敏感字段脱敏
    ↓
返回
```

华南区运营查「上个月销售额」，系统自动补上 `WHERE region = '华南'` ，他看不到华东的数据。

## 六、结果别只给个表格

### 6.1 数据呈现三板斧

NL2SQL 返回结果别只甩一个表格，三层呈现：

**第一层：数据表格** — 原始结果，给需要细看的人

**第二层：自动选图** — 结构决定图表类型。时间序列→折线图，分类对比→柱状图，占比→饼图

**第三层：一句话解读** — 简单分析结论，让人一眼看懂

### 6.2 处理不了的，别硬编

```
用户：查销售额
系统：您想查哪个时间范围？近7天、近30天、上月还是自定义？

用户：查转化率
系统：「转化率」有不同口径——
     A) 下单转化率（下单用户/访客数）
     B) 支付转化率（支付用户/下单用户）
     您指哪种？

用户：查竞品的销售额
系统：当前系统没有竞品数据，我只能查内部数据。
```

宁可多问一句，不要猜错了糊弄人。

### 6.3 用户反馈是宝藏

每次用户确认或修正，都是训练样本。把（问题, 正确SQL, 用户修正后的SQL）存下来，积累到一定量级直接拿去做 Few-shot 样本。哪些查询容易出错、语义层缺了什么字段，从反馈数据里全看得到。

## 七、提前想清楚的风险

### 准确率不够怎么办

别一上来碰复杂查询，L1 做到 99% 再往下推。语义层先行，把复杂逻辑预定义。用户看到错误结果时，提供「查看/编辑 SQL」功能，让他有掌控感。

### 查询太慢怎么办

缓存命中率拉到 60% 以上。大模型推理加排队，简单查询用小模型，响应控制在 500ms 以内。慢查询自动拆分或走预计算。

### 权限绕过怎么办

权限校验在 Schema 链接阶段就做，不是最后拦截。所有查询写审计日志，敏感操作加审批流程。

### 用户期望太高怎么办

明确告知能干什么、不能干什么。留一个「数据需求提报」通道兜底。持续收集反馈，快速迭代。

---

## 八、写在最后

设计智能问数平台，NL2SQL 技术本身只是其中一环。

语义层怎么建，决定了准确率有多高；权限怎么管，决定了企业敢不敢用；体验怎么做好，决定了用户愿不愿用。

一句话总结：语义层做准、分层模型做省、权限控制做稳、对话体验做好。
