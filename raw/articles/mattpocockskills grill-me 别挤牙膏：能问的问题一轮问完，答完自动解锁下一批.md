## 前言

之前我们在 [04 - mattpocock/skills 为啥不让我直接写代码？grill-me 让你怀疑人生](https://mp.weixin.qq.com/s?__biz=MzYyMTQ4MDI1OA==&mid=2247484057&idx=1&sn=12d2da9f6cf44655ec2fc7efa6169559&scene=21#wechat_redirect) 讲过 grill 家族，核心纪律有一条，一次只问一个问题。grilling 的原文说得很直接，一次问多个问题会把人问懵。

这条纪律是对的，但用久了你会发现一个尴尬的场景。

你给 AI 讲了一个新功能的设想，AI 开始访谈。第一个问题，你答了。第二个，你答了。第三个，你答了。然后它问第四个、第五个、第六个，每个都要等你想一下，再回一句。这个功能的决策点有点多，二十个问题排着队，你答到第八个，开始走神了。答到第十五个，你已经只想说「都行，你看着办」。

问题出在哪？不是问题太多，是节奏不对。一次一个问题，对「需要深入思考」的决策是好的，但对「大部分是确认」的批量决策，就太磨叽了。就像让你一个一个地签字，签二十张表，每张表还要你重新读一遍。

`/batch-grill-me` 换了个玩法：别一个一个来了，把当前能问的所有问题，打包成一轮，一次性问完。

它不是把 grill 的问题一次全抛给你。它有一套严格的机制，保证批量提问不会变成乱问。这套机制的核心是三个词：设计树、前沿、轮次。一个一个拆。

照例先把话说在前面。batch-grill-me 和 loop-me 一样，都在 Matt 的官方仓库 `skills/in-progress/` 桶里挂着，属于草稿技能，不在插件包和官方 README 里，得自己从源码装。但它的规则已经相当完整，值得现在就学。

## 一、grill 家族现在有几个成员了

先更新一下家族谱。04 课讲了三兄弟。

grilling 是内核循环，一次一个问题，模型自动调用。

grill-me 是轻量壳，你手动输入，问完就走。

grill-with-docs 是重量壳，问完还写文档，产出 CONTEXT.md 和 ADR。

loop-me 专题加了一位，loop-me，问完写 workflow spec，把生活循环写成委托说明书。

batch-grill-me 是第五位，它的不同之处全在一个词上，batch，批量。同样是 grilling 的内核精神，它把「一次一个问题」改成了「一轮一批问题」。

```
grilling（内核：一次一个问题）
├── grill-me（轻壳，问完就走）
├── grill-with-docs（重壳，问完写 CONTEXT.md / ADR）
├── loop-me（问完写 workflow spec）
└── batch-grill-me（一轮问完整个前沿）
```

这里有个绕不开的疑问：04 课说一次问多个问题会把人问懵，batch-grill-me 这不是打脸吗？

不是。区别在「怎么问」。grilling 反对的，是把一堆毫无组织的问题甩过去，每个都要你从零想。batch-grill-me 的批量，是结构化的：问题按依赖关系排好，本轮只问「前置已定」的那批，每个都带推荐答案，你做的不是思考，是确认。认知负担完全不同。这个区别，看完整篇文章就懂了。

## 二、设计树：访谈的骨架

batch-grill-me 把一次访谈想象成一棵树，叫设计树。

每个决策是一个节点，挂在它下面的，是依赖它的子决策。比如「会员等级按什么算」是根节点，它下面挂着「分几个档位」「升级什么时候生效」，因为不先定按什么算，档位和生效时机都没法答。

树长什么样，访谈就怎么走。只能问那些「前置条件已经定了」的节点，因为问别的是在猜你还没听到的答案。

这就是前沿（frontier）的定义：所有前置已定的决策，也就是现在就能问、不用猜的问题集合。

一句话版本：前沿 = 现在可以问的问题。树的边界每前进一步，前沿就往外推一步。

## 三、轮次：一轮问完整个前沿

batch-grill-me 按轮进行。每一轮，把当前整个前沿一次问完。

格式是固定的：每个问题编号，每个问题附一个推荐答案。然后停下来，等你答完这一批，再进下一轮。

为什么带编号？二十个问题排好序，你回答时能对号入座，不会漏。

为什么带推荐答案？这是 grill 家族的老规矩了。访谈不是考试，是过方案。AI 先给建议，你确认或修改，速度能快一个数量级。批量场景下这一条尤其重要，二十个问题每个都带建议，你二十分钟能过完，否则两小时都未必。

关键规则在这：一个问题，如果它的答案依赖本轮另一个还没答的问题，它就不属于这一轮，属于更晚的轮次。绝不猜。

每轮你答完之后，树就变了。已定的决策把前沿往外推，原来被它们卡住的问题解锁了。重新算一遍前沿，问下一轮。如此反复，直到前沿为空。

## 四、事实归 agent，决策归你

grill 家族的老纪律，batch-grill-me 继承并且加强了：找事实是 agent 的事，永远不是你的。

当某个前沿问题需要环境里的事实，比如代码库的结构、某个表有没有字段、某个工具支不支持某能力，它不问你，直接派一个子代理去查。

更讲究的是不阻塞。子代理在跑的时候，只有依赖这个事实的下游问题等着，其余的前沿问题照问不误。你不用干坐着等它查完，该答的答，查完的报告回来，再解锁依赖它的问题。

你只需要做一件事：拍板。所有「选哪个」的决策是你的，它逐个问你，等你回答。事实、调查、验证，全是它的活。

## 五、完成标准：前沿空了

batch-grill-me 什么时候算问完？一句话：当前沿为空的时候。

前沿为空，意味着设计树的每一个分支都走过了，没有任何一个该问的问题被静默假设掉。没有「这个应该没问题吧」的漏网之鱼。

在你确认双方达成共享理解之前，它不会动手做任何事。访谈归访谈，实现归实现，中间隔着你的一句话。

## 六、手把手，把 EShop 会员等级访谈一遍

理论说完了，来真的。场景：给 EShop 加会员等级功能，需求一句话，用户消费越多等级越高，等级高折扣大。

先看这棵设计树长什么样。

```
会员等级（根决策）
├── 按什么累计？订单金额？订单数？购买次数？
│     ├── 分几个档位？
│     ├── 升级什么时候生效？即时还是次日？
│     ├── 历史订单算不算？
│     └── 各档折扣率怎么定？
└── 事实：订单表能否支撑按金额累计？
      └── 缺字段的话怎么办？
```

第一轮。根决策的前置是空的，能问。两个事实问题，交给子代理查，不阻塞。

```
AI 第 1 轮：
  1. 会员等级按什么累计？订单金额、订单数还是购买次数？
     推荐答案：按累计实付金额，这是电商最常见也最不容易刷的指标。
  2. （子代理已派出：查订单表结构，能否支撑按累计实付金额统计）
     报告回来后我们再看。

你：按累计实付金额，同意。
```

第二轮。你的回答定了根决策，三个子决策解锁。子代理的报告也回来了，订单表有支付金额字段，够用，顺带把「缺字段怎么办」的分支剪掉了。

```
AI 第 2 轮：
  1. 分几个档位？
     推荐答案：三档，普通 / 白银 / 黄金。
  2. 升级什么时候生效？
     推荐答案：即时生效。用户这笔订单支付成功，立刻升到对应等级。
  3. 历史订单算不算？
     推荐答案：不算，从会员功能上线后开始累计。理由：老订单的支付金额口径和历史优惠对不上，追溯会引入争议。
  4. （子代理报告：订单表有 paid_amount 字段，可以直接统计，无需加字段。）

你：档位三档可以，升级我要次日生效，历史订单从上线后算。
```

注意，你改了第二题的答案。这没问题，树照常重塑。次日生效这个决策，又解锁了下一轮的两个问题：升级任务谁跑、跑挂了怎么处理。

第三轮，也是最后一轮。

```
AI 第 3 轮：
  1. 各档折扣率？
     推荐答案：白银 95 折，黄金 9 折。普通无折扣。
  2. 次日生效的升级任务，什么时候跑？
     推荐答案：每天凌晨跑一次，按前一天的累计金额结算。
  3. 结算任务失败怎么办？
     推荐答案：记录失败并告警，第二天重跑，幂等处理，不会重复升级。

你：折扣可以，结算任务凌晨两点跑，失败告警后人工介入，不用自动重跑。
```

三题答完，前沿空了。树的每个分支都走过了，没有静默假设。AI 总结一遍确认理解一致，访谈结束，你可以放它去干活了。

这场会话是我按 batch-grill-me 的规则模拟的教学示例，不是真实录音，但机制是真实的：一轮问完整个前沿、问题编号加推荐答案、依赖问题留到下一轮、事实派子代理查、前沿空即完成。

对比一下 04 课 grill-me 的那场访谈，同样是问需求，grill-me 是四个问题一个一个来，batch-grill-me 是三个批次二十个问题（这例子是 3 + 3 + 3）。功能越复杂，问题越多，batch 的优势越明显。

## 七、什么时候用 batch-grill-me

两个都姓 grill，用哪个？

grill-me（以及它背后的 grilling），适合决策点少、每个决策都需要深思的需求。它给每个问题留足思考时间，一次一个，不容易疲劳。你新功能就三五个关键决策，用它。

batch-grill-me，适合决策点多、大部分决策其实心里有数、只想快速过一遍的需求。它把「确认式」的问题批量处理，你集中回答，效率高得多。你脑子里已经有七八成方案，用它把剩余的两三成补全，顺便让 AI 把所有边角都扫一遍。

一个直觉的判断方法：你答到第几个问题会开始烦？

五个以内，grill-me。超过十个，batch-grill-me。中间地带，随你心情。两个都是同一个内核的变体，随时可以换，不影响正确性，只影响节奏。

## 八、边界和误区

第一，batch 不是让你甩手不管。批量提问的前提，是每个问题都带推荐答案、按依赖排好序。它省掉的是你的思考成本，不是你的拍板责任。每个答案你都得过一遍，别全盘接受。

第二，别用它问「需要深思」的决策。有些决策，比如定价策略、技术选型，值得一次一个慢慢想。批量模式会把它们淹没在一堆琐碎问题里，你随手就答了，答完才发现没想清楚。这类决策，回到 grill-me。

第三，它是访谈工具，不是实现工具。前沿空了，只是「问完了」，不等于「做完了」。访谈结果怎么落成 spec、怎么拆工单，是 to-spec、to-tickets 的活，别指望它一步到位。

第四，依赖关系是它的命根子。如果你发现 AI 在问一个依赖尚未回答的问题，它在违规，提醒它重新算前沿。这是它唯一的硬规则，值得盯。

## 九、为什么值得学

往回看，grill 家族的演进其实是一条线：怎么让「访谈」这件事更快、更省力、还不失严谨。

grill-me 确立了内核：一次一个问题、带推荐答案、事实自己查。grill-with-docs 加了沉淀：问完写进文档，下次不用重问。loop-me 加了定向：只问工作流，直接产出委托说明书。batch-grill-me 加的是批量：把整个前沿打包，一轮过完。

每一步都是在跟同一个敌人作战：需求访谈太慢，人们就不想访谈，需求就不清，AI 就瞎猜。batch-grill-me 把「慢」这个最大的劝退因素砍掉了一大截。

它顺带教会你一个更通用的思维：任何要梳理清楚的事情，都可以画成一棵树，先问前置已定的，再把依赖它们的逐个解锁。这个「按依赖分层推进」的思考方式，不依赖任何工具，用在哪都成立。

## 快速回顾

- 家族谱： grill 家族第五位，batch-grill-me，区别全在 batch 二字
- 设计树： 访谈被建模成树，每个决策下挂依赖它的子决策
- 前沿（frontier）： 前置已定的决策集合，即现在能问的问题
- 轮次： 一轮问完整个前沿，问题编号、附推荐答案，答完再进下一轮；依赖本轮未答问题的，留到更晚轮次，绝不猜
- 事实归 agent： 子代理查环境事实，不阻塞，只有下游问题等报告
- 完成标准： 前沿为空，每个分支都走过，没有静默假设；确认共享理解前不动手
- 取舍： 决策少要深思用 grill-me，决策多要快速过用 batch-grill-me，答到第几个开始烦就是判断标尺
- 状态： in-progress 草稿技能，官方仓库 `skills/in-progress/batch-grill-me` ，自己从源码装
