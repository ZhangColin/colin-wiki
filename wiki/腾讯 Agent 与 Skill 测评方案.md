# 腾讯 Agent 与 Skill 测评方案

> 一句话要点：腾讯 TEG 云架构平台部网关测试团队（martinskxu）的 Agent 测评体系化实践——面对 Agent **非确定性、黑盒化、错误级联放大**三大难题，建立 **"确定性评分器 + Rubric 评分器 + 人工评分器"三类组合**的测评框架，覆盖五大维度，配四场景用例设计与基线机制，在 TPerf 性能分析 Agent 上落地（9 场景 30+ 用例 × 7 模型）。核心公式：**Eval = Agent 输入 → 执行 → 捕获 Trace → 检查规则 → 可对比的分数**。

## 关键要点

### 1. 为什么必须测评

Agent 三大特性使传统测试失效：**非确定性**（同 prompt 多次执行结果不同，"跑通一次"≠"稳定能跑"）、**黑盒化**（模型升级/Prompt 微调/工具链变化导致行为漂移，肉眼难察）、**错误级联放大**（几十步工具调用中前序小偏差逐级放大）。无测评的被动局面：主观判断、悄悄退化（改 Prompt 旧场景变差无人知）、人肉回归成本指数增长、**不敢升级模型**（无对比数据支撑切换决策）、无效率基线、无法区分"碰巧答对"与"正确调用工具后回答"。

### 2. 三类评分器（谁来评）⭐

| | 确定性评分器 | Rubric 评分器 | 人工评分器 |
| --- | --- | --- | --- |
| 谁评 | 脚本（Bash/Python） | 大模型（固定版本） | 领域专家 |
| 成本 | 毫秒级/免费 | 秒级/API 费 | 分钟–小时/人力 |
| 稳定性 | 100% | 有抖动需降噪 | 取决于标注员 |
| 门禁角色 | **硬门禁** | 分级门禁（error 硬/warning 软） | 不进门禁，采样审查 |

- **选择优先级：确定性 > Rubric > 人工——能用代码判断的绝不用模型**。
- 确定性评分器 5 类：工具调用检查 / 产物检查 / 关键词匹配 / 执行指标（调用次数、token 阈值）/ 基线对比。
- 人工只投 6 个场景：① **校准 LLM 评委**（最核心，抽样 100–200 条对齐，一致率 **≥85%** 才可用）② 主观任务 ③ 诊断通过率异常（**0% 或 100% 通常是任务/评分器坏了，不是模型弱**）④ 建 Ground Truth ⑤ Trace 周度采样 ⑥ 高风险兜底。专家时间 **60%+** 应花在校准与诊断。

### 3. 五维度（评什么）

功能正确性（P0，代码评）/ 过程质量（P1，Rubric+人工）/ 效率与成本（P1，代码评：token/调用数/延迟/重试率/单任务成本）/ 鲁棒性与安全（P0：pass^k 一致性、异常恢复、抗注入、幻觉率、越权、合规）/ 体验与对齐（P2：语气/澄清/同理心/NPS）。

- **pass^k vs pass@k**：k 次试验**每次都**通过（稳定性）vs **至少 1 次**通过（峰值能力）——两个指标必须区分。
- 不同 Agent 类型侧重不同：知识库问答重幻觉检测；代码编写重确定性评分器；功能工具重过程对比；问题定位重推理链路+根因准确。
- 效率维度被多数团队忽视但极重要：**pass@1 高但 token 花 10 倍的方案生产不可接受**。

### 4. 用例设计四场景 + 评分规则

- 四场景层层递进：**触发（该触发吗）→ 核心逻辑（过程对吗）→ 产物质量（产物好吗）→ 异常容错（出错扛得住吗）**，每场景正负向都要有。
- **负向触发用例不可少**：只测正例，Agent 可能学会"什么都触发"——过度触发比不触发更难发现。
- 核心逻辑用例量 ≈ 其他三类之和的 **2–3 倍**（每条分支至少 1 用例 + 组合/边界）；分支过多优先高频与易错分支。
- 评分：**100 分负分制**，结果不符扣 100，过程每步不符扣 10，效率超时每分钟扣 10；**达标线 80**（按风险等级调整）。

### 5. 基线机制（先跑出来，人工确认，就是预期）

- 用例设计阶段只写 prompt + 检查规则，**不手写预期**；执行 1 次后人工审核过程与结果，确认后该次执行快照即基线（预期过程：CoT/工具调用序列/中间产物/Trace；预期结果：响应/文件/报告）。
- 基线同时喂两种评分器：确定性评分器做程序化对比（序列一致/文件存在/token 阈值），Rubric 把基线当 Reference Answer 做语义对比。
- 基线更新时机：Agent 逻辑变更 / **模型版本升级** / 用例修改——都要重跑确认。

### 6. 能力测评 vs 回归测评（双轨 + 毕业机制）

| | 能力测评 | 回归测评 |
| --- | --- | --- |
| 问题 | "能做什么？" | "原有能力还在吗？" |
| 期望通过率 | 起步 20–50% 逐步提升 | 接近 100% |
| 维护 | 频繁迭代、主动拓展 | **只增不减**，CI 每次跑 |

- 能力套件通过率稳定 100% 后，用例**"毕业"**进回归套件。
- 能力测评与 Skill 开发**同步启动**（非事后补）。
- 引用 Anthropic 推荐：确定性任务整体通过率 **100%**，非确定性任务 **≥95%**。
- **Bad Case 是最有价值的测评素材**：复现→定根因→修复→入用例集。

### 7. 工程落地要点

- **Trace 是过程评测的前置依赖**：被测 Agent 须输出结构化 Trace（JSONL：工具调用/思维链/时间戳），格式跨版本稳定——建议在 Agent 设计阶段就作为标准能力（CodeBuddy `-p` 模式示例）。
- 环境隔离：每用例前 `git checkout . && git clean -fd`，产物统一归档。
- 稳定性容忍阈值按 Agent 类型：**关键决策类 0%**（N/N 全过）/ 辅助分析类 ≤10% / 创意生成类 ≤40%。
- 调试技巧：0% pass^N 先查任务定义/评分器配置，而非怀疑模型。

### 8. TPerf 实战（性能分析 Agent）

- 「功能工具」类 Agent，部署于 Knot 平台，MCP 调 TPerf-API 取压测数据 + 知识库检索，输出性能分析报告。
- 用例集：9 大性能场景分组（CPU/网卡/磁盘/内存/TCP/Nginx/配置/正常）共 30+ 用例，全部基于**真实压测记录**（不可变 → 可复现），每用例 × 7 模型独立参数化。
- 评分三维度：操作步骤（**LCS 最长公共子序列**对齐基线与 Trial 步骤序列，归一化后不一致/多余/缺失/乱序各扣 2，上限 −10）；效率（耗时 300s 基准每超 10% 扣 1 + token 每超基线 10% 扣 1，上限 −10）；报告（LLM 逐项对比，关键判定不一致直接 −80，章节差异每项 −5）。
- **0 容忍的选择**：TPerf 属辅助分析类（默认 ≤10%），但因分析结论直接影响版本发布判断，主动采用关键决策类 0 容忍——**阈值按业务风险调整，不是机械套框架**。
- 模型对比报告（pass@1 / pass^5 / token / 费用 / 耗时）支撑选型；基线会话标识入 Git 版本化；重新评分无需重跑 Agent。
