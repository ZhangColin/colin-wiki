# 子代理驱动开发

> 一句话定义：[[Superpowers]] 的核心执行模式——"Fresh subagent per task + two-stage review"，把大任务拆成独立子任务，每个子任务由一个干净上下文的子代理实现，再经独立审查；上下文隔离防污染、独立审查防护短。

## 核心观点

### 为什么需要子代理

- **上下文隔离**：主代理（controller）若边想边写，working state 会被早期决策污染；每个 task 派给 fresh subagent（干净 context）实现，避免漂移。
- **防自审护短**：main agent 写完代码会护短（"我写的，挺好"）；拆给独立 sub-agents 审查更客观。这是"作者和审查者绝不在同一上下文里互评"的根本理由。
- [[Jesse Vincent]] 原则：执行者应被假设为 "an enthusiastic junior engineer with poor taste, no judgement, no project context"，故必须隔离 + 审查。

### 两阶段审查（v5.x）→ 单 reviewer（v6.0）

- **v5.x**：每个 task 后跑两轮独立 review——第一轮规格符合性（查"缺失"与"多余"），第二轮代码质量（风格/边界/性能）。必须按序。
- **v6.0 结构性变更**：合并为单一 `task-reviewer`，"reads the task's diff once and returns two verdicts"（少读一遍 diff、少起一个 subagent）。详见 [[Superpowers 6.0 reviewer 只读重写]]。
- **v6.0 reviewer 三特质**：① 只读（曾发生 reviewer 跑 `git checkout` 致孤儿提交）；② 怀疑论者（"Do Not Trust the Report"，implementer 自述不能降低发现严重性）；③ controller 禁止辅导 reviewer（禁止告诉 reviewer 不要标记什么）。

### Model 纪律

- **v5.x 痛点**：派 subagent 不指定 model → 静默继承 session 顶配（一次运行 26 个 reviewer 全跑顶配）。
- **v6.0 修复**：两模板开头强制声明 model——"an omitted model silently inherits the session's most expensive one"。
- **反直觉规律**：便宜模型多步任务要跑 2-3 倍轮次反更贵，故按复杂度匹配档位（机械实现用快速/廉价模型、集成判断用标准模型、架构/审查用最强模型），"不要用旗舰级模型去定义 DTO"。

### 教学化口径：两级审查 = 自审 + 复审（老谭幸福账本系列，2026-09）

[[Superpowers subagent-driven-development AI 项目经理]] 给出中文教学版框架——主会话当项目经理：读计划 → 拆任务 → 派子代理（各用各的 worktree，任务单含文件边界 + 验收）→ **两级审查**（第一级子代理自审：跑测试贴结果 + 对照验收自查；第二级主会话复审：读代码、对照计划、查契约一致性、抓夹带私货）→ 打回须说清理由 → 合并 + 主干再测。与官方两口径并排：v5.x 两轮**独立** review（审查者与实现者不同代理）→ v6.0 单 task-reviewer（只读怀疑论者）；教学版把第一级降为**自审**——与"防自审护短"的原始动机有张力（官方靠独立 reviewer 解决，教学版靠主会话复审兜底）。两个清醒剂值得收录：① **项目经理质量上限 = 计划质量**（"喂得好是项目经理，喂得烂是无头苍蝇"）；② **项目经理也在你的上下文里干活**——拆的任务越多上下文越挤，须分批（与 [[smart zone]] 会话预算纪律同题）。与 [[Superpowers dispatching-parallel-agents 并行派发]] 的分工：dispatching = 人拆好人肉派发，SDD = 整个功能委托给 AI 拆派审。

### 外部印证：builder/validator 彻底分离（Cole Medin 黑灯工厂，2026-08）

[[Cole Medin 黑灯工厂实验]] 把"作者与审查者绝不在同一上下文里互评"推到极致——**builder 不知道测试，validator 不知道计划**：编码 agent 会对自己刚写的东西心软，validator 既不知道实现也不知道计划，只看产物；验收标准（holdout 场景）对 builder 完全保密，防"挟持验收标准"。与 Superpowers v6.0 怀疑论只读 reviewer（"Do Not Trust the Report"）独立同构——**信息隔离是防自审护短的通用解**，跨框架成立。

### 外部印证 2：TAB 4-Agent 契约与"下游不可改上游"（2026-07）

[[TAB 大仓 Harness 工程化实战]] 的 4 个认知 Agent（需求/方案/开发/代码审查 + 总控）给出**角色契约**形态——每个角色明确"必读 / 必写 / 不许做"三栏（审查 Agent 不许改代码只产出阻塞项，开发 Agent 不许超出设计范围）：

- **最重纪律：下游 Agent 不可直接修改上游产物，只能提阻塞项由总控打回**——解决的不是技术问题，是责任边界问题（方案 Agent 顺手改验收标准 → 审查时分不清哪句是产品的、哪句是 AI 加的）。
- 审查 Agent 的"**方案一致性**"维度专门抓 **AI 解释性执行**（实现到一半觉得"设计写得不好我顺手改一下"）——与"fresh subagent 防主代理护短"同一问题的两种表述。
- 演进教训：单 Agent 跑全流程"天然缺乏制衡 + 倾向往前推进 + token 爆炸"→ 被撞墙一步步逼出 4 Agent；反向纪律"**能用 Skill 解决就别开 Agent**"（Skill = 虚拟子 Agent，无状态无 turn 成本）。

### 外部印证 3：任务图 + 前沿 + 集成分支（mattpocock v1.3，2026-10）

[[Matt Pocock implement-spec 拆解]] 给出第三种形态——同为「编排者 + 实现子代理 + 独立审查 + worktree」，分歧在**调度依据与审查时机**：SDD 按计划逐 task、每 task 审查（v6.0 单 reviewer）；implement-spec 按**任务图**（票带阻塞边）以**前沿**（frontier）维持最大并发、成果快进并进**集成分支**、终点跑一次 code-review——「任务图定节奏，前沿定人数，集成分支定终点，指针代替寒暄」。两版互参：**审查密度换并发吞吐**；implement-spec 明言「交付的是草稿，评审才完成它」。

### Progress Ledger 对抗 compaction 失忆

git-ignored 的 `progress.md` 每完成一 task 追加一行；compaction 后 controller 读 ledger + git log 恢复进度；"trust the ledger and git log over your own recollection"。官方称重派整套已完成 task 是"观测到的最昂贵失败模式"。

### 上下文经济学（v6.0）

5.x 把 task 文本和 diff 粘进 dispatch prompt，永久占用 controller context；6.0 用三脚本（`task-brief`/`review-package`/`sdd-workspace`），subagent 读文件而非接收粘贴，单独省约 10% token 和时间。

## ⚠️ 矛盾 / 未解问题

- **两阶段审查描述在 v6.0 后已过时**：[[Superpowers 7阶段交付SKU库存扣减]] 与 [[Superpowers 7步闭环工作流深度指南]]（v5.x 时代）详述"两轮独立审查"，v6.0 已合并。读旧页时注意版本。
- **审查口径三版本并存（2026-09 更新）**：v5.x 两轮独立 review → v6.0 单 task-reviewer（只读怀疑论者）→ 老谭教学版"子代理自审 + 主会话复审"（[[Superpowers subagent-driven-development AI 项目经理]]）。教学版未体现"审查者与实现者不同上下文""reviewer 只读"等硬约束——判为教学化简化（或对应某中间版本），引用时注意区分。
- writing-plans 结构变更：v6.0 每个 task 必须带 Interfaces block（Consumes/Produces 精确签名），因 implementer 只看自己 brief。
