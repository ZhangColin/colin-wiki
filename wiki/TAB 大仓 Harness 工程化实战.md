# TAB 大仓 Harness 工程化实战

> 一句话要点：[[腾讯程序员]]（fitchzheng、leoshli，TAB A/B 实验平台团队，2026-07-07）在 30+ 微服务 / 10+ 前端微应用 / 多 submodule 大仓上搭 Harness 的完整复盘——"不讲理念，只讲怎么搭起来、怎么撞墙、撞完怎么补"。核心诊断：**跑不完一个需求不是模型问题，是协作、流程、信任问题**；核心手法：六层资产 + 13 棒接力 + 4 Agent 契约 + 7 道门禁（基线对比剥夺解释权）+ 5 个人工关卡。

## 关键要点

### 1. 背景与诊断

- TAB = 腾讯公司级 A/B 实验平台（Go/TS 为主，胶水层→接口→服务→领域四层，7 切面横切链）；一行 PRD 可能牵动 3 子仓库、5 协议字段、8 服务方法、12 单测、2 接口测试。
- 四大真实卡点（**没有一件是模型问题**）：PRD 不能被信任（删除会不会触发下游回收？幂等吗？）/ 方案对不上代码 / 改完没人验证（"我改完了"≠"跑过沙箱接口测试且增量覆盖率 ≥85%"）/ 交付环节碎成一地（TAPD/iWiki/工蜂/企微全靠人记）。
- **SPEC-First**：第一步不是写 Rule 拆 Agent，而是先磨全链路技术设计文档——拆四个子目标、划清"AI 能跑什么 vs 必须人介入"、定义一期边界。"没有这份 SPEC，Harness 不会被搭出来，**会被搭歪**——Harness 不是一组工具，是一种工程纪律，纪律必须先有共识。"

### 2. 六层资产 ⭐

| 层 | TAB 上的形态 | 核心判断 |
| --- | --- | --- |
| Rule | **几乎没写** | 自然语言天然被"解释性执行"（"这条不适用/我做了等价的事/这是历史问题"）→ **能判定的就别留在 Rule 里**，全部下沉 lint/脚本/静态扫描 |
| Skill | 11 个，四组（脚手架规范 4 / 测试规范 2 / 需求理解 3 / 审查 2） | **Skill 不是能力增强，是注意力管理**——把"怎么做"从主 prompt 拆出去，防规范淹没需求上下文、防改一条规矩每个 Agent 都要同步 |
| Sub Agent | 只留 4 个：需求/方案/开发/代码审查 + 总控调度 | **能写成 bash 的就别让 Agent 跑**——流程调度/门禁/测试/MR 是纯确定性工作，让 AI 解释执行只徒增 token 与不确定性 |
| Workflow | 13 棒接力赛（初始化→需求分析→需求确认→[Bug复现]→技术方案→[方案确认]→方案评审→分支准备→开发→集成测试→代码审查→验收→交付收尾） | Agent 间是**接力关系不是协商关系**；流程定义抽成可校验资产（定义文档+伪代码状态机+自检脚本） |
| Scripts | 7 道门禁 | **把"完成"的定义权从 AI 口头汇报里拿回来** |
| MCP | 5 个（TAPD/iWiki/工蜂/Knot/企微） | **MCP 不是 Harness 主体，是外接能力接口**——从开发闭环扩展到交付闭环的最后一段路 |

- 13 阶段不能合的判断标准只有两条：**有独立的失败模式？失败时回退位置不同？** 两个"是"才独立。

### 3. 门禁设计（第六章，作者自认最有共鸣）

- 7 道门禁 3 硬 4 软：硬 = 静态检查+安全扫描、沙箱部署、接口测试；软 = 覆盖率（全量 ≥40% 且增量 ≥85%）、制品一致性、前端冒烟、日志验收。
- **硬门禁宁少不多**：不是质量红线就别阻断——频繁打断会让团队怀疑工程化价值，退回 Vibe Coding。
- **基线对比反作弊** ⭐：开发前跑一次门禁"基线快照"（失败集合 A），开发后跑"差异"（失败集合 B），**只有 B−A 新增失败才阻断**——"历史问题"这把万能钥匙被拿掉。价值不在技术，**在于剥夺 AI 的解释权**。
- **软门禁失败留"伤疤"**：警告记录 + 代码审查结论显式提及 + 度量报告沉淀——"**你不能阻止 AI 偷懒，但你可以让偷懒变得很醒目**。"

### 4. 4 个 Agent 是被撞墙逼出来的（演进史）

1. **单 Agent 跑全流程** → 上下文混杂（分不清 TAPD 写的和它推断的）、天然缺乏制衡（自己审自己几乎不否决）、**倾向往前推进**（反复说服自己继续）、token 爆炸（1M 不够）。
2. **拆需求/方案 Agent** → 立刻见效（方案 Agent 暴露边界假设）；但方案 Agent 会顺手改验收标准 → 定下**最重纪律：下游 Agent 不可直接修改上游产物，只能提阻塞项由总控打回**——解决的是责任边界，不是技术。
3. **拆代码审查 Agent** → 收口 4 维度：**方案一致性**（防"AI 解释性执行"——实现到一半觉得"设计写得不好我顺手改一下"）、验收标准覆盖、质量基线、前端增量；只产出阻塞项，不许改代码。
4. **开发 Agent 扩职责**（不是拆）→ 集成测试前置后，"开发完成"= 业务代码+单测+**接口用例文档+增量接口测试**——"**让产生问题的人，同时产生验证手段**"。
- **不再拆**的理由：四层架构强依赖，并行收益小协调成本高；**Skill 本质是"虚拟的子 Agent"**——能用 Skill 解决就别开 Agent（Agent 带状态带 turn 带 token 成本，Skill 是无状态文档加载）。

### 5. 集成测试前置的故事（最值得分享的弯路）

最早接口测试放在验收（代码审查之后）→ 死循环：审查 Agent 仔细审完 200 行 diff → 验收跑接口测试挂 → 打回开发 → 重审。**最贵的环节背最便宜的锅**（接口测试几秒能验证）。前置为硬门禁后：代码审查平均打回 **1.8 → 0.4 次**。
- 反向取舍：Bug 复现从"所有 bugfix 必走"改为**条件触发**（TAPD 单写清楚的不必复现）——"**流程要给明显已经清楚的事留快车道**，强制所有需求走最严路径 = 惩罚准备充分的需求"。

### 6. 人工关卡（第五章）

- 试过 Reviewer Agent 判方案，不行：**"模型对自己生成的东西天然没有否决欲望"——模型层偏置，prompt 控不住**，下游 Agent 99% 觉得上游"看上去挺好"。→ **关键节点必须有人**：不是不信任 AI，是承认 AI 现阶段不擅长"否决自己人"。
- 5 个关卡：需求确认（10–30 秒）/ 方案确认（40% 需求触发）/ 方案评审打回（<10%）/ 前端冒烟三选一（5 秒）/ **熔断暂停**（任意阶段连续打回 ≥3 次）。
- 硬约束：**"不能让用户每分钟点一次以上"**——体感不对，团队会主动绕过工具退回 Vibe Coding。任何每分钟点一次以上的交互都是设计 bug。
- 三级兜底：UI 按钮 / 纯文本关键词 / 语义识别——人工关卡不是"等待输入"，是"以最低摩擦听懂人想干什么"。

### 7. Team Mode 撞墙复盘（第七章，密度最高）

- 症状：需求确认关卡必现卡死（输入"确认继续"后主 Agent 无响应）。三轮错诊（标记残留/虚假超时/按钮不匹配）全部无效。
- 真相：主 Agent 的本轮对话跨越子 Agent 执行时间，抛出确认提示后本轮已结束；Team Mode 把用户输入路由到主控收件箱——**消息有目的地，但目的地下班了**。
- 解法不是修 bug 而是**删机制**：4 个 spawn 点全是串行单个，从没用过 Team Mode 的并行能力——其复杂度只为解决自己引入的问题（**"复杂度自给自足"陷阱：一个机制主要在 fix 自己的副作用时，80% 该删**）。改用项目级子 Agent + 同步阻塞调用，卡死消失，主 Agent 代码反而少 200 行。
- 三条方法论：警惕自给自足复杂度 / **先 grep 自己的代码再修 bug**（早点确认"从没用过并行能力"就不浪费三轮）/ **YAGNI**（保留可选路径=维护两套协议）。

### 8. 项目记性：仓库文档 vs Memory（第八章）

- 痛点：AI 重复造轮子（工具方法/错误码/数据访问已存在又写一遍）——不是模型不够强，是没有"项目记性"。
- 两层仓库内索引：**代码导航地图**（约 26KB，开发 Agent 谁动谁更新；需求 Agent 先读全景索引段再进需求理解，避免 80%"在错的子仓库里改"）+ **任务看板**（总控维护的跨需求 checkpoint，防"新需求冲掉旧设计"）。
- ⭐ **Memory vs 仓库文档**："仓库文档是团队共识，能审计、能交接；Memory 是个人偏好，看不见、对不齐。4 个工程师同时跑 Harness，4 个人的 Memory 会互相矛盾。"纪律：**团队要对齐的东西必须落到仓库，Memory 只放纯个人偏好**。

### 9. MCP 原则（第九章）

- 5 个 MCP 定位：**不是给 AI 万能钥匙**——每类外部交互收敛成有明确入参、语义、审计痕迹的方法；通用 HTTP 工具让 AI 自己调 = 事故只是时间问题。
- 三句话原则：**读多写少**（写方法严格挑，想清楚重复调用会怎样）/ **写操作只在初始化与交付收尾两个阶段触发**（其余一概只读——"AI 半路改坏外部系统状态"消失）/ **全部留痕**。
- 四条踩坑：先做开发闭环再接 MCP / 写操作必须幂等（判重后跳过）/ MCP 失败软降级只警告不阻断 / 能用 MCP 就别用子进程 OAuth2（收敛单通道）。

### 10. 成果与四块拼图

- 50+ 真实需求后：端到端 30–75 分钟（不含人工等待）、人工介入 2–3 次、集成测试一次通过 ~70%、代码审查阻塞率 ~25%（多为"方案一致性"维度）、开发打回 0.4 次。限制：PRD 完整度强相关（一句话需求耗时翻倍）、≥3 子仓库变慢、前端+后端混合最难。
- 四块拼图：**约束与流程 / 反馈 / 知识库 / 进化**——缺约束则边界被冲掉，缺反馈则"改完了"全靠口头，缺知识库则重复造轮子，缺进化则不知上次为何这么定。
- 永远不要做：第一天拆 7 个 Agent / 让 AI 跑确定性脚本 / 让下游改上游产物 / 全设硬门禁 / 无基线对比就信"历史问题" / 团队规约存进 Memory。
- 金句："**AI 的瓶颈早就不是模型，是协作、流程、信任。**""**半自动比全自动更难，但更值得做——它是当前 AI 能力下唯一稳定可推广的形态。**"

- 成果数字（70% 一次通过率、25% 阻塞率、50+ 需求）为团队自述，无第三方复核；且未说明对照基线（没有 Harness 时代的数据）。
